Design Brief · Klauro

Entry points: every way into a running system

A plain-language guide to a body of data Klauro produces, written so you can decide how and where to present it. It describes what the information is and the shape it comes in — the presentation is yours to design.

Audience: design Scope: one deployable at a time Tests: out of scope Numbers: from a live analysis

Start here

What we're describing

Klauro analyzes a codebase and, among many things, finds every entry point — every place where something outside a running program can reach in and make it do work. One quick way to picture it: if a deployable (one independently running piece of software — an API server, a web app, a background worker) is a building, the entry points are the doors. That's the last we'll lean on the metaphor — from here we just call them entry points.

A system typically has more entry points than people expect, and they're not all the same kind. Some you knock on and wait for an answer. Some are mail slots — you drop something off and walk away. Some trip on their own when the environment changes. The job of this information is to make that full set legible at a glance — how many, of what kinds, how they're reached, whether they're protected, and what each one sets in motion.

Who looks at this, and why

An engineer or architect new to a system asking "how is this thing reached — what's its usage surface?" · A security reviewer asking "what's exposed to the public versus protected behind a login?" · Anyone gauging integration points or blast radius before making a change. The through-line: the surface area of contact between this system and the outside world.

One thing to hold onto: this is always per deployable. A web app's entry points are pages and button clicks; an API server's are tool calls and messages. The same system can contain both, and they look nothing alike. The viewer is always looking at one deployable, with the ability to switch to another.

The mental model

Three families of entry point

This is the most important structure in the dataset. Every entry point falls into one of three families based on how the interaction behaves — a split Klauro already computes. The counts are from a real analysis, tests excluded.

Reacts on its own

Passive
The motion-sensor lights — no one calls them; the environment trips them.

Nothing external "calls" these. The system's own runtime or operating environment triggers them — the app starting up or shutting down, a file appearing in a watched folder, a hardware signal. Easy to overlook, which is exactly why surfacing them earns its keep.

In this family: startup & shutdown lifecycle, file watchers, hardware / timer signals.

The mix is the system's character: a heavy tool-call surface says "built for AI agents"; a heavy message surface says "event-driven backend"; a heavy pages-and-clicks surface says "user-facing web app." A reviewer reads the shape before reading a single row.

One kind lives in two families

An event can be either: a UI click is request-and-wait; a published or consumed event is send-and-forget. Context decides which family it belongs to — worth knowing if you build anything that keys off the family.

The key relationship

Every entry point opens into a flow

An entry point is not the end of the story — it's the beginning of one. The moment an entry point fires, the system runs a flow: the ordered sequence of steps that entry point sets in motion. There is one flow behind every entry point, and it's the answer to the question a list of entry points immediately provokes — "okay, but what does it actually do?"

So the entry point and its flow are a pair: the entry point is how you get in, the flow is what happens next. The natural interaction is to move from one to the other — select an entry point, and drop into the flow it triggers.

Each flow carries its own detail, ready for a deeper view: what it takes in, the data it touches, the outside services it calls along the way, what it returns, and where it ends. That richness lives on the flow, not the entry point — so however this is presented, leave a door open from each entry point into its flow rather than trying to show everything in one place.

Why this matters for the design

It means an entry-point view is a starting surface, not a terminal one. The reader lands here to get oriented — the counts, the kinds, what's protected — then follows the thread inward to a specific flow. Designing the step from entry point into flow is as important as the catalog itself.

One rung higher

Most entry points ladder up to a capability — but not cleanly

There's one more link, and it's the subtlest one in the brief. If a flow is what happens when an entry point fires, a capability is why it exists — the business thing the system does. Klauro names these too (in this analysis: "Analyze a codebase," "Detect patterns," "Trace and monitor"). So the ladder runs entry point → flow → capability:

Why it exists

But that last link is not one-to-one, and not universal — this is the part to design carefully around, because a naive "each entry point belongs to one capability" will misrepresent the system. Three things are true:

  1. It's many-to-many, with a role each way

    One capability is realized by many flows; one flow can serve several capabilities. And a flow carries a role for each tie — it's the primary flow that realizes one capability, and merely supporting for others.

  2. Cross-cutting entry points belong to (almost) everything

    Authentication is the clearest case — the auth flow isn't the point of any single capability; it supports nearly all of them. Same for logging, validation, rate-limiting. These recur across many capabilities by design, so an entry point can legitimately map to a long list, not one.

  3. Some entry points serve no capability at all

    Build and deploy scripts, health checks, internal plumbing — real entry points whose flow has a role of infrastructure. They ladder up to nothing on the business side, and that's correct, not a gap.

With that understood, capabilities unlock a second way to organize the same entry points — by purpose instead of by mechanism. Rather than "here are 207 tool calls," it becomes: "the Analyze a codebase capability can be triggered five ways." That's usually the question a person actually arrives with — "how do I make it do X?" — and it surfaces health signals a flat list can't: a capability with no entry point (built but untriggerable), or a capability reachable only one way (a single point of entry).

What this means for a by-capability view

Design it to hold three shapes at once: an entry point that belongs to one capability, one that belongs to many (auth, health), and one that belongs to none (infrastructure). A layout that assumes a tidy one-to-one will break on the first cross-cutting entry point — and every real system has them.

Made concrete

What those fields actually contain

Several fields above are abstract until you see them filled in — and the important thing is that their content changes with the kind of entry point. A web endpoint's inputs are body fields with types; a command's are flags; a scheduled job has none. Here's the real content to expect, so you know what any container for these has to hold. (Examples use Klauro's own API.)

What it expects

the “input”

Usually a list of named inputs, each with a type and a required-or-optional marker. For some kinds it's command flags or a message payload instead — and for others, nothing at all. A field's type can be a plain value (text, number) or a named type with its own definition — the same range as returns, below. Your container needs to hold a short list of “name · type · required?”, read well when the list is empty, and let a named type link deeper.

What it returns

the “output”

This one has the most range, so it's worth spelling out. A return value can be a named type — a class or interface that has its own definition elsewhere, which means the return can be a link deeper, not just a label. Or a loose object with inline fields. Or a plain value. Or a list. Or one of several things. Or nothing at all. On top of that, request-and-wait entry points also carry outcome codes (the success and the failures). Your container has to hold all of these gracefully — and treat a named type as something the reader can follow, the way they follow a flow.

Whether it's protected

the “security”

This is more layered than a lock icon. First the plain state — open to anyone or protected. Then, when protected, four separate things, and an entry point may carry any mix: how you prove who you are (the method — an access token / JWT, a login session, an API key, a sign-in provider, a client certificate); who's allowed (the roles — the RBAC layer); what permissions, scopes, or claims a caller must carry; and any limits (a rate cap). Your container needs an at-a-glance state, plus a home for each layer when it's present.

Security may deserve its own view — worth settling early

Security is the one dimension rich and cross-cutting enough that it might not belong inside the entry-point view at all. Beyond the per-entry summary above, Klauro computes it at the system level: the boundaries a request crosses (an "authentication boundary," enforced by middleware), whether each is actually enforced or only assumed, and — the part a reviewer cares most about — a list of sensitive operations left unprotected. That's a whole story of its own. A reasonable shape: a dedicated security view that aggregates boundaries, enforcement, roles, and the unprotected-surface risk list, while the entry-point view keeps a compact per-entry summary that links into it. Whether security lives here, there, or both is a real fork to decide up front.

The live layer

What we know once it's running

Everything so far is read from the code without running it — static. But an entry point also has a life at runtime, and Klauro can capture it: how often it's actually called, how often it fails, and how fast it responds. This is a different kind of data — streamed from the running system — and it turns the catalog from a map into a health view. It's the one part of the picture that's about the present moment, not the code.

Small as it is, that changes what the view can answer:

  • Live vs. dormant — which entry points are actually used, and which are built but never called (dead weight, or a security surface no one's watching).
  • The hot paths — the handful of entry points carrying most of the traffic, worth the most care.
  • The trouble spots — high error rate or a slow tail, the ones to look at first.

It's only there when the system is reporting

This data exists only for a deployment that's running and instrumented — a system Klauro has analyzed but that isn't sending telemetry shows none of it. So treat the live layer as present sometimes, absent others: the static picture always stands on its own, and the runtime numbers enrich it when they're there. Design the entry-point row to look complete without them, and better with them.

More ways to cut it

Other dimensions you could organize by

The three families and the capability view are the two big organizing ideas, but the same entry points carry several other dimensions. Any one could be a grouping, a filter, a sort, or a color. These are the ones grounded in real data — a few need data we're still filling in, marked accordingly.

Protected vs. publicBehind a login versus open to anyone — the security lens. The most compelling cut for a reviewer.
External vs. internalReachable from outside the system, or only by sibling deployables. This is the true "attack surface" — what the outside world can actually touch.
Used vs. dormantneeds dataHow often each entry point is actually hit, from live traffic — the live doors, the dead ones, the error-prone ones. Turns a static catalog into a health view.
Registration surfaceKlauro already pre-groups entry points that are wired up the same way (e.g. "the tool-call surface") — a ready-made grouping you can lean on.
Resource / domainThe noun a set of endpoints clusters around — everything under "projects," everything under "workspaces." A familiar way to browse an API.
First-party vs. frameworkDid a developer write this, or is it a framework default (a health check, a lifecycle hook)? Separates the signal from the boilerplate.
Reach / blast radiusHow much of the system sits behind an entry point — which doors open onto the most.

The mirror image: exit points

Entry points are how the system is reached. The same analysis also finds exit points — how the deployable reaches out: to databases, other services, message buses, caches. In this analysis there are 1,227 of them (802 database, 331 libraries/SDKs, 58 outbound APIs, 20 messages). Ways-in and ways-out together are the complete surface of contact between this system and everything around it. Whether that belongs on the same view or a neighbouring one is your call — but it's worth knowing the other half exists.

Design around these

The shape of the real data

Five facts about how this data actually looks — the ones most likely to make a naive treatment fall apart.

  1. The count ranges wildly

    A small service might have a dozen entry points; a large one, a couple of thousand. This analysis has 737 (excluding tests). The design has to feel right at both a dozen and two thousand — which usually means summarize-first, with search and grouping to reach any single one, not a scroll of everything.

  2. The distribution is extremely lopsided

    A couple of channels hold hundreds of entry points; many hold one or two. If every category gets equal visual weight the result feels wrong — the big surfaces need room to breathe and the long tail needs a compact treatment. A one-item group shouldn't claim the same real estate as a two-hundred-item one.

  3. The names aren't always friendly

    Roughly a third of entry points are labeled with raw code names — main, handleRequest, do_thing — not clean phrases like "Analyze a codebase." Your treatment of the name has to hold a tidy sentence and a terse code token without looking broken, and probably show the address right alongside so a cryptic name isn't the only handle.

  4. Detail varies by kind

    A web endpoint naturally carries a rich contract — inputs, outputs, who's allowed. A lifecycle hook carries almost nothing but a name. Whatever you design has to look intentional both when an entry point is detail-rich and when it's a bare label. Plan the sparse case first.

  5. The character shifts hard per deployable

    Switch from the web app to the API server and the whole complexion changes — pages-and-clicks become tool-calls-and-messages. This isn't one flat list with a filter; it's a context the viewer stands inside. Switching deployables should feel like changing rooms, not re-sorting a table.

Don't forget the in-between states

The happy path — a rich, fully-populated entry point — is the easy case to design. The ones that decide whether this feels solid: a deployable with no entry points found; an analysis still running; an entry point with only a name and address and nothing else; no telemetry because the system isn't reporting. Each of these is common, not exceptional. A design that only looks right when everything's present will look broken most of the time.

And what a person does from here. Worth deciding whether this is a reference to read or a tool to operate — the data supports either. From a single entry point, the natural moves:

  • Get oriented — read the counts, the families, what's protected, what's live.
  • Follow it inward — open the flow it triggers, to see what actually happens.
  • Jump to the code — for a technical viewer, straight to the file and line.
  • See its purpose — the capability it serves, and what else serves that capability.
  • Cross to security — from a protected entry point into the fuller security picture.
  • Slice the whole set — group, filter, or sort by any of the dimensions above.
