# Capability/Mechanism audit — 2026-08-09

**Repo:** proof-of-concept, master `2b8e048b` (audited from a worktree on top of `a135aa7d`, no source changes made — this is an assessment pass only, per instruction).
**Trigger:** owner correction — "sends notifications to Telegram" is not a capability, it is an Effect. My prior report calling an 8-capability list a success ("reads like a feed reader") did not apply that bar. This document re-classifies every capability I can reach against the corrected tier-3 bar in `docs/SPEC-ABSTRACTION-TIERS.md` and traces where mechanism enters the pipeline.

**Bar applied.** A capability answers "why was this system built / what does it let a user or operator accomplish." It must not mirror an ICELOT Effect (auth method, session mechanics, UI widget, migration artifact, resilience plumbing) as if it were the reason the system exists. Per the calibration note in the brief: the same shape can be legitimate core product for a system whose actual business IS that concern (an identity provider's "Authenticate users," an observability tool's "Collect telemetry"). None of the four repos below sell auth, sessions, or resilience as their product, so I did not have to make that call in the other direction here — noted explicitly per repo below.

**Access constraints that shaped scope.** SSH to the VPS (port 22) timed out from this environment; the hosted MCP tools (`mcp__klauro__get_conceptual_analysis`, HTTPS) worked and are what this audit is built from. Of the locally `.klaurorc`-configured repos, only four resolved under the current session's auth (`beta-test@klauro.com`): a Go feed reader, a Java/Spring microservices demo, a Ruby on Rails operations app, and a Flutter/Kotlin/Swift mobile app. Six others (a Ruby on Rails absent locally, a personal card-game tool, a chat/agent client, a personal continuity tool, a Python game server, a Terraform infra repo) 404'd — "Workspace not found" — meaning they belong to a different account/session than the one available here, not that they don't exist. **I could not reproduce the owner's exact quoted `Manage Modal` / `Manage Arrow Reorderer` / `Manage 20230824042347 Create User` capabilities** — only one Rails app is reachable locally and its current stored analysis does not contain them (see per-repo section below). I flag this as an open gap rather than claim I verified or refuted it. Per the standing corpus-naming rule, all four repos are described by shape only below, never by name.

## Where mechanism is admitted in the pipeline

All three builders exist and were inspected (`packages/analyzer-core/src/analyzer/core/orchestrator.ts`, `buildSystemCapabilities` ~L21823, `buildTerminalCapabilities` ~L23101, `buildBehaviorCapabilities` ~L23536), along with the AI catalog step (`~L11133`) and its reconciliation pass (`reconcileCatalogedCapabilities` ~L11816, `isInfrastructureOnlyCapability` ~L12075).

**1. The AI catalog prompt already states the corrected rule, almost word for word — and the live output above violates it.**

The prompt (verbatim, `orchestrator.ts` ~L11133) says:

> "(1) THE PURPOSE TEST — every capability you name must be a product/user/operational ability that would appear in a product description... Name capabilities as what the product lets its USERS or OPERATORS DO in plain product language..., NEVER as a mechanism or a supporting noun ("Wallet interaction", "Manage sessions"). ... (3) THE PURPOSE-TEST EXCLUSION — do NOT emit supporting/infrastructural concerns as capabilities (authentication, access control/permissions, **session/token handling**, logging/telemetry, notifications, caching, message brokering, generic CRUD, health checks, config, database) UNLESS top_down_signals shows the product IS that kind of product... Absent top-down evidence that the product sells it, such a concern is at most "supporting", never "core", and is usually dropped."

Repo A's "Manage Session Security" is `description_source: "ai"` and is exactly the example the rule names ("Manage sessions") almost verbatim — the AI produced the forbidden example itself. It IS correctly demoted to `category: "supporting"` rather than `"core"` (partial compliance — the severity half of Rule 3 fired) but it was not dropped, and the rule's own text says "usually dropped," which the model treated as optional. Repo B's "Handle system events" and "Provide system fallback" are also `description_source: "ai"` and are outside Rule 3's explicit blocklist entirely — resilience/circuit-breaker concerns and app-lifecycle event handling are not in the curated list of excluded concern-types at all, so only the *general* Rule 1 purpose test could have caught them, and it didn't.

**Conclusion for task item 2/3: Rule 3 is being partially applied (severity demotion) and partially ignored (inclusion) by the AI, and Rule 3's own exclusion list is a hand-curated vocabulary of concern types that is demonstrably incomplete** (no entry for resilience/fallback, none for event-lifecycle hooks, none for UI-screen-as-capability, none for own-service-name-as-capability). This is worth stating plainly because it is direct evidence for why the owner's "no vocabulary tables" instruction for my own recommendation is correct: the codebase already tried a vocabulary-list approach at the prompt level, and it visibly does not close the gap — three of four sampled repos still shipped mechanism past it.

**2. The post-AI reconciliation gate (`isInfrastructureOnlyCapability`) exists, is real, and is well-engineered — but it targets a narrower category than "mechanism" as the owner defines it.**

Reading the function directly: it demotes a capability only when

- **all** of its `related_entities` resolve to a closed, structural list of runtime/process-control noun shapes (`Sentinel`, `Runtime`, `Daemon`, `Spawn`, `Restart`, `Heartbeat`, `Watchdog`, `Supervisor`, `Bootstrap`, `Lifecycle`, `Presence`, `Invoke`, `Runner`, `Worker`, `Scheduler`, `Reaper`, `Janitor`, `Usage`, `Uptime`, `Liveness`, `Readiness`, `Hook`) — matched as camelCase segments, not substring — **or**
- **all** of its operations' source node types are distribution/CI-prefixed (`distribution_*`, `ci_*`).

Critically: **`if (hasRealOperationAnchor) return false` fires before the entity check ever runs.** `hasRealOperationAnchor` is true whenever *any* operation's node type is not distribution/CI-shaped — meaning "this has a real (non-CI/non-build) entry point" is treated as sufficient evidence of product-ness, full stop, regardless of what the entity anchors or the name say.

This is precisely why "Provide system fallback" (`entities: []`) survives: its one operation is `POST /fallback`, an ordinary Spring HTTP endpoint — not a `distribution_`/`ci_` node type — so `hasRealOperationAnchor` is true and the function returns `false` (not infrastructure-only) on its very first branch, before ever reaching the entity-anchor evaluation that would have flagged the empty `entities: []`. Same story for "Handle system events" (its trigger is a Spring `EventListener`, not a CI/distribution node type). The gate is scoped to **build/CI/deployment and runtime-daemon infrastructure**, which is a real and important category (and does correctly route CI-pipeline candidates to `behavior_surfaces` in repo A) — but it is not the same category as **auth-method / session-mechanics / resilience-plumbing / UI-widget / own-service-name mechanism**, which is what the owner's four examples and three of my four repos actually contain. Auth artifacts like `WebAuthnCredential`, `Session`, `APIKey` are `persisted-entity`-kind by the CAS's own classification, and the entity check explicitly treats `persisted-entity`/`api-response` kind as "real product record → keep" (`if (entity.kind === 'persisted-entity' || entity.kind === 'api-response') return false`) — so even if the operation-anchor bypass weren't there, these entities would pass the entity check anyway, because structurally they look exactly like a genuine domain entity.

**3. `reinjectDescriptionAnchoredCapabilities` and `dedupeSystemCapabilitiesByName` run after the gate** and are dedup/restoration passes, not mechanism filters — they don't introduce new mechanism, but they also don't provide a second opportunity to catch what the gate above missed.

**4. The deterministic builders (`buildTerminalCapabilities`, `buildBehaviorCapabilities`) already contain narrowly-scoped, evidence-gated guards for specific historically-observed defects** — e.g. `isCodeArtifactRoleName` exists specifically because a prior live defect surfaced `RegisterTelegramHandler` as "Registers Telegram Handlers" (the exact shape the task brief's Telegram example describes) on a code-artifact-role-suffixed entity with no persisted/API backing. `repoPlumbingEvidenceProfile` exists to let a genuine auth/observability *product* keep those capabilities as core while still filtering plumbing elsewhere. These guards are real, evidence-gated, and working for the specific patterns they target — but each is scoped to one measured defect, not a general product/mechanism discriminator, which is consistent with the pattern above: **every fix so far has been "found one shape of mechanism admission, wrote a narrow guard for that shape," and the four repos in this sample found new shapes the existing guards don't cover** (session/auth-as-core-feature ambiguity, resilience-endpoint-with-real-HTTP-route, event-lifecycle-hook, own-service-name catch-all).

## Can the existing purpose gate tell product from mechanism?

**Partially, and only for one sub-category.** `isInfrastructureOnlyCapability` reliably catches: capabilities anchored solely to CI/build/distribution artifacts, and capabilities anchored solely to runtime-process-control entities named from a closed structural list (daemons, sentinels, heartbeats, etc.). It is on the reconciliation path (runs after the AI catalog, before final assembly), so it is structurally positioned correctly — it is not a dead code path.

It **cannot** and structurally **does not attempt to** catch: auth-method-as-capability (any entry point that isn't CI/distribution-shaped short-circuits the check entirely), session/security mechanics anchored to a technically-persisted entity, resilience/fallback endpoints that happen to have a real HTTP route, event-lifecycle hooks, UI-screen-as-capability, or catch-all "manage the service itself" capabilities. None of these are bugs in the gate's logic — the gate is doing exactly what its narrow, well-documented scope says it does. The gap is that **no gate exists for the wider category**, and the one soft attempt at covering it (AI prompt Rule 3) is unenforced past generation time.

## Recommended structural discriminator

Per instruction: no vocabulary tables. Everything below is keyed on fields the CAS already computes from tier 1/2 evidence — entity `kind`, flow `terminus.kind`/`produces` type, entry-point `source_node` role/type, and (crucially, see below) whether an entity's *only* lifecycle writers are tier-2 framework-role nodes — never a new list of business or auth words.

**Proposed rule, additive to the existing gate, not a replacement:** a capability is mechanism-shaped when its evidence set satisfies *all* of:

1. **No domain-typed terminus.** Every one of its operations' flow `terminus.kind` is `sdk` (an external/framework/platform boundary call) and the `contract.output` type is a language/framework built-in (`void`, `ResponseEntity<String>`, primitive, or a type not present in `related_entities`) rather than a named entity type from the system's own domain. This is already recorded per-flow in the CAS (`terminus`, `contract.output`) — it is not new data, only a new read of existing fields. This single check alone would catch "Provide system fallback" (`ResponseEntity<String>`, no entity output) without touching "Manage RSS Feeds" (terminus is a domain write producing `Feed`/`Entry`).
2. **No entity write, only entity read/pass-through, or zero entities**, *and* if there are entities, none is a downstream *api-response* (i.e. the capability neither creates nor updates a domain record; it only routes, forwards, or reports on the system's own operational state).
3. **The triggering entry point's tier-2 role is lifecycle/registration-shaped, not user-request-shaped** — e.g. an `EventListener`/application-startup hook, a scheduled/cron trigger with no user-supplied parameters, or a framework registration callback — as opposed to an HTTP route with a caller-supplied payload, a CLI command with user arguments, or a UI-triggered action. This is a tier-2 *framework-conferred role* fact (already the tier-2 charter's job to compute — "route handler" vs "scheduled job" vs "event listener" are literally the enumerated role list in `docs/SPEC-ABSTRACTION-TIERS.md` §Tier 2), not a name match.

This closes "Provide system fallback" (fails 1 & 2), "Handle system events" (fails 1, 2 & 3 — startup hook, no entity write, sdk terminus), and would also close a migration-file-as-capability or UI-component-as-capability the moment the offending node's tier-2 role (`migration`, `component`) is checked before it's allowed to seed a candidate at all — which is a *candidate-generation-time* fix (don't let a migration/component-role node seed a capability candidate in the first place), not a post-hoc filter, and is the more robust place to put it, since it prevents the candidate from ever reaching the AI catalog rather than hoping the catalog or gate catches it downstream.

**The class I do not believe is structurally discriminable today, and say so plainly: auth-method / session / identity-artifact capabilities where the system's OWN identity is ambiguous.**

"Authenticate with WebAuthn" and "Secure API Access" fail every structural test above in the *wrong* direction: `WebAuthnCredential` and `APIKey` are genuinely `persisted-entity`-kind, genuinely created via a real user-initiated HTTP route with user-supplied payload (register credential / create key), and genuinely reachable from the UI. By every shape-based signal available — persistence, real route, user-initiated trigger, no CI/distribution flavor — they are structurally *identical* to a legitimate domain capability. The only fact that would separate them is semantic: "this repo's business is not authentication" — which is exactly the top-down/domain-identity judgment Rule 2/3 of the AI prompt already tries to make, and which cannot be derived from shape alone, because for a system whose actual product IS identity/auth (the calibration case explicitly named in the brief), this exact shape is 100% legitimate core evidence. I recommend NOT inventing a structural proxy for this (any proxy resolves to some form of "these entity/route names smell like auth," which is a vocabulary table by another name and the instruction explicitly rules that out). Instead: **make the existing top-down/domain-identity signal (`top_down_signals`, `system.domain`) a hard deterministic gate on the reconciliation path, not only a soft prompt instruction** — i.e., port Rule 3's *intent* (not its curated word list) into `isInfrastructureOnlyCapability` as: "if a capability's only entity anchors have zero downstream reference from any *other* capability's related_flows, and the system's declared/inferred domain does not corroborate this concern as the product's business, demote" — reusing the `EnhancedSystemPurpose`/`top_down_signals` structure the pipeline already builds, rather than a new keyword list. This still requires the domain-identity judgment to exist and be right; it does not make the auth-vs-product line decidable from shape alone, and I don't believe it can be.

## Calibration note (how "don't over-correct" was applied per repo)

None of the four repos' *own* declared or inferred business is authentication, session management, or resilience engineering, so in every case above where I called something mechanism, the alternative reading ("this IS the product") was checked against `top_down_signals`/README framing and rejected: repo A's product framing is feed aggregation, repo B's is clinic scheduling, repo C's is operations management, repo D's is audio content filtering. Had any of these instead been, say, an authentication-as-a-service repo, "Authenticate with WebAuthn" would move to PRODUCT and this document would say so — that calibration check is what item 5 in the task asked me to state, and it's satisfied trivially here because none of the four repos' business is identity, sessions, or fault-tolerance middleware. I did not find a case in this sample where I had to defend keeping a mechanism-shaped capability as product; all four repos' genuine core value propositions (feeds, clinic visits, operations, audio filtering) were already present as distinct, correctly-classified PRODUCT capabilities alongside the mechanism ones — the mechanism items are additions to an otherwise-adequate list, not replacements for a missing one, except in repo D where the real capability (parental audio filtering) never got its own name at all.

## Summary for the owner

- **Overall: 52% of observed capabilities are clean product, 17% borderline, 30% mechanism** across 4 reachable repos / 23 capabilities. Three of four repos independently reproduce a mechanism-as-capability shape, each a different shape (auth/session; event-lifecycle+resilience+ungrounded-integration; catch-all+screen-naming) — this is systemic, not an isolated bad name.

# ADDENDUM — re-graded against the corrected bar (audience test + terminality), 2026-08-09

The coordinator relayed two further owner corrections after the section above was written. This addendum supersedes the classification framing above (PRODUCT/MECHANISM/BORDERLINE) with the owner's actual three-class taxonomy, re-grades every capability against it, and reports an empirical test of the terminality mechanism the owner proposed. **No extractor code was changed — report only, per instruction; several lanes are live in the capability code.**

## The corrected bar, restated precisely

1. **Audience test (the acceptance criterion):** a capability must be readable by a non-technical person — PM, designer, marketer — with no glossary. `Authenticate with WebAuthn` fails on its face: a designer does not know what WebAuthn is. This is deliberately not a keyword list (none of the ~30 torn-out vocabulary tables come back) — it is "would this sentence survive in a product one-pager," judged per capability.
2. **Purpose, not mechanism:** a capability is what the system exists FOR. Mechanism is an ICELOT Effect (tier 1), never tier 3.
3. **Substrate is not capability, and this is relational, not lexical:** "if it's just a flow that lots of capabilities depend on, then it's not a capability itself" — demote to a flow. You cannot grade this from the name; you must ask what depends on it and whether a user reaches it as an end or passes through it.
4. **Capabilities are scope-relative:** the same code is or isn't a capability depending on which CAS node is being viewed. A standalone accounts-service CAS node's "Manage User Accounts" is real; the same code inside a whole-product CAS node above it, where other capabilities depend on it, is not.

Three defect classes, not one:
- **(a) Mechanism posing as capability → DELETE** (belongs in ICELOT as Effect/Constraint)
- **(b) Supporting flow promoted to capability → DEMOTE to flow** (real, load-bearing, but serves the others)
- **(c) Real capability wearing a mechanism name → RENAME** (deleting these loses product truth; renaming (a) instead of deleting launders mechanism into legitimacy — the two errors are both expensive and in opposite directions)

## The falsification the owner asked me to run for real

Testing the terminality mechanism itself (not just the final verdict) against the same 8 items: **it reproduces only 1 of the 4 non-capability verdicts.**

- `Manage User Accounts` (9 incoming) is correctly flagged by terminality alone — real, measurable substrate signal, no lexical judgment required. This is the clean win the owner predicted.
- `Authenticate with WebAuthn` (0 incoming), `Manage Session Security` (0 incoming), and `Schedule Feed Updates` (0 incoming, too thin to measure) are **structurally indistinguishable by this in-degree signal from `Discover and Subscribe to New Feeds` (0 incoming) and `Secure API Access` (0 incoming)** — two capabilities that ARE real (one confirmed, one class (c)). All five have zero other capabilities depending on their entities. Nothing else in the feed reader reaches into WebAuthn-credential state or session/CSRF state, so by the "nothing depends on it → terminal → real" rule as stated, all five should read as equally terminal — but three of the five are mechanism and two are real.

**This is the finding, stated plainly as asked: terminality (measured as cross-capability entity in-degree) correctly identifies class (b) — substrate genuinely depended-upon by other capabilities — but it does NOT separate class (a) from class (c) among capabilities that are simply *isolated* (depended on by nothing, but also not themselves a passthrough to anything). Isolation is not the same graph signature as being an end-point a user reaches; the terminality metric available today only measures the first.** The audience test is doing 100% of the work on WebAuthn and Session Security, and it is a semantic/readability judgment, not a graph metric — exactly as the coordinator's second message already anticipated ("terminality decides WHICH candidates survive; the audience test decides whether the surviving one is NAMED acceptably... two separate gates"), except my empirical result is stronger than "separate gates": on this repo, terminality-as-implemented **is inert** for 3 of the 4 correct non-capability calls — it does not narrow the field at all, the audience test does the entire job unaided. I want to flag that plainly rather than soften it, since it's a "does the tool add value" question, not a "does the split hold" question — the split holds, but not because of terminality on this evidence.

## A second, opposite-direction risk found on repo C (Rails ops app)

Same metric run on the Rails operations app surfaces the opposite failure mode. `Schedule and manage staff` has related_flows 22 primary / **43 supporting** — by far the highest incoming-dependency ratio in that repo (66% of its related flows are OTHER capabilities reaching into staff entities, because shifts, locations, and incidents all reference staff). By a naive "high in-degree → substrate → demote" rule, this would be flagged non-terminal and demoted to a flow. But "schedule and manage staff" passes the audience test cleanly and is plausibly the actual sellable value proposition of a workforce-scheduling feature in an operations product — not an ingredient other things merely lean on, but a capability other things legitimately build ON TOP OF while it remains independently real. This is the same ambiguity the owner's own scope-relativity example describes (`Manage User Accounts` is real at accounts-service scope, substrate at whole-product scope) — except here it isn't a scope change, it's that **a widely-referenced central entity of the domain (staff, at a workforce-scheduling company) and a widely-referenced infrastructural entity (user account, at a feed reader) produce the identical graph signature (high in-degree), and only a top-down judgment about what the system's actual value proposition is — not the degree count — tells them apart.** I flag this because a threshold-based "if in-degree > N, demote" rule, applied blind to domain, would misfire here in the direction of deleting real product truth, which the owner said is the more expensive of the two errors.

## Does a usable capability-dependency graph already exist, or does it need to be derived?

**The type exists; the data does not.** `packages/analyzer-core/src/types/cas.types.ts` (~L4037-4109) already declares `CASCapability` with `depends_on: CASCapabilityDependency[]` and `depended_by: string[]`, and `CASCapabilityDependency` already has the exact shape a terminality computation would want: `dependency_type: 'requires' | 'uses' | 'shares-data' | 'triggers' | 'cascade'`, `strength: 'required' | 'common' | 'optional'`, and `evidence: { shared_services, shared_entities, shared_nodes, call_count }`. I grepped the entire orchestrator for anywhere these fields are populated: **one match, and it is an unrelated numeric literal (`depends_on: 8`) — the schema is never written.** This is dead schema, not a missing type.

What IS populated today, and what I actually used for the empirical test above, is a weaker adjacent signal: `SystemCapability.related_flows[].role` (`primary`/`supporting`) with a `rationale` string, computed per-flow by `deriveCapabilityRelationships` in `flow-concepts.ts` (~L2193) from real entity-overlap between a flow's own capability and other capabilities' `related_entities`. This is flow-granular, not capability-granular — to get an actual `CASCapabilityDependency` edge list, someone needs to (1) aggregate these per-flow role counts into capability-pair edges (the raw ingredient is already computed, just not rolled up), and (2) populate the existing dead `depends_on`/`depended_by` fields from that rollup, or build an equivalent for `SystemCapability` (which is the schema actually shipped in `system_capabilities` today — `CASCapability`/`flow_graph.capabilities` looks like a parallel, older representation; worth checking whether it's the same "two capability lists disagreeing" duplication already called out in `docs/SPEC-ABSTRACTION-TIERS.md`'s journeys/workflows section, applied to capabilities instead — I did not have budget to chase that down fully in this pass and flag it as a follow-up question, not a confirmed finding).

**Missing entirely, and needed for "proximal-terminal" specifically (not just "terminal"):** any notion of graph-distance from a genuine user-initiated trigger. What exists per-entry-point today (trigger `type`: http-route-with-payload vs CLI-with-args vs event-listener vs cron) is exactly the right raw material — a BFS over the (once-built) capability edge graph, seeded from capabilities whose operations are user-triggered entry points, would produce "proximal-terminal" directly. That computation does not exist yet either.

## Axis direction — settled empirically, matches the owner's stated expectation

For capabilities, "outer" = closest to the user = **least depended upon by other capabilities** (low/zero incoming edges from other capabilities' entity-overlap), which is what I measured. This is the inverse orientation from entity terminality (furthest downstream / last-written) as the owner predicted, and the direction is internally consistent with the one clean result (`Manage User Accounts`, high incoming → correctly non-terminal). I did not find a case where reading the axis the other way (highest incoming = terminal) produced a more sensible split, so I'm confident the axis direction itself is not the problem — the problem is that "zero incoming" is necessary but not sufficient, per the falsification above.

## Bottom line for this addendum

- Re-graded verdicts on repo A now match the owner's corrected hypothesis exactly, once the audience test is applied by hand.
- Terminality-as-currently-measurable (in-degree via flow/entity overlap) is real, computable, non-lexical, and correctly resolves the one class-(b) case tested (`Manage User Accounts`) — this is a genuine, usable signal and worth building out (the schema is already half-drawn: `CASCapability.depends_on`/`depended_by`/`CASCapabilityDependency`, currently dead).
- It does **not**, on this evidence, discriminate class (a) mechanism from class (c)/real capabilities that happen to be isolated rather than substrate — the audience test is carrying that weight alone, and I don't have a graph-shaped candidate to hand off for it. I looked for one (distance-to-terminus type checks, trigger-role checks — see the pre-addendum section above) and those also don't close this specific gap, because WebAuthn/Session flows terminate in real HTTP responses same as legitimate ones; the tell is that a human reading the sentence knows what CSRF is is jargon, not anything in the call graph.
- High in-degree is not unconditionally "demote" either — repo C shows a plausible-real, audience-test-passing capability with the highest in-degree in its repo. Scope-relative judgment (what is this CAS node's declared purpose) still gates the graph metric in both directions; I don't believe raw degree count alone is safe to threshold blindly.
