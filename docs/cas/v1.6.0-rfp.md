# CAS v1.6.0 Request for Proposal - Test Architecture & Visualization

**Version:** 1.6.0 RFP
**Status:** Draft
**Created:** 2026-01-23
**Supersedes:** v1.5.0

## Executive Summary

This RFP proposes CAS v1.6.0 to address critical gaps in test representation, categorization, and visualization. The enhancements enable comprehensive test analysis including type categorization (unit/integration/e2e), BDD support, mock tracking, test-to-code relationships, and coverage integration.

## Problem Statement

### Current Limitations (v1.5.0)

1. **No Dedicated Test Entry Point Type**: Tests are incorrectly marked as `type: 'event'` with `metadata: { event: 'test' }`. This is semantically wrong - tests are not events.

2. **No Test Categorization Schema**: No way to distinguish between unit, integration, e2e, acceptance, or performance tests.

3. **No Test-to-Code Relationships**: Tests are detected but not linked to what they test. Cannot answer "what tests cover this service?"

4. **No BDD Support**: No representation for Given/When/Then patterns, Cucumber/Gherkin scenarios, or feature files.

5. **No Mock Tracking**: Mocks are detected but not linked to what they replace. Cannot answer "what is this mock substituting?"

6. **No Coverage Integration**: Coverage data exists separately but is not linked to CAS nodes. Cannot show "this function is 80% covered by these tests."

7. **No Test Summary**: No aggregated view of test health, coverage by layer, or test type distribution.

### User Impact

- Frontend cannot display tests separately from events
- Test visualization is flat (no grouping by type, domain, or coverage)
- Cannot drill down from "Users" domain to "User tests"
- Cannot filter tests by type (show only integration tests)
- Cannot identify which code has no test coverage
- Cannot see BDD scenarios in human-readable format
- Mock relationships are invisible

### Root Cause

The CAS spec lacks:
- Dedicated `'test'` entry point type
- Test categorization metadata schema
- Test-to-code edge types (`tests`, `mocks`, `covers`)
- BDD step representation
- Test suite and test case structures
- Mock and fixture node relationships
- Per-node coverage data

## Proposed Solution

### 1. New Entry Point Type: 'test'

```typescript
interface EntryPoint {
  type: 'http' | 'grpc' | 'graphql' | 'websocket' | 'cli' |
        'event' | 'scheduled' | 'startup' | 'test' | 'other';  // ADD 'test'
  // ...existing fields...
}
```

**Semantic Rules:**
- Tests MUST use `type: 'test'`, NOT `type: 'event'`
- Tests previously marked as events with `metadata.event === 'test'` MUST be migrated to `type: 'test'`

### 2. Test Metadata Schema

```typescript
interface TestMetadata {
  test_type: 'unit' | 'integration' | 'e2e' | 'acceptance' |
             'performance' | 'visual' | 'smoke' | 'bdd';
  test_style: 'procedural' | 'bdd' | 'property-based' |
              'snapshot' | 'parameterized';
  priority: 'critical' | 'high' | 'medium' | 'low';
  tags: string[];
  uses_mocks: boolean;
  is_async: boolean;
  timeout_ms?: number;
  framework: string;  // 'jest', 'pytest', 'rust-test', 'mocha', 'cypress', etc.

  bdd_context?: {
    feature?: string;
    scenario?: string;
    given?: string[];
    when?: string[];
    then?: string[];
  };

  parameterization?: {
    data_source: 'inline' | 'fixture' | 'external';
    parameter_count: number;
    cases: number;
  };
}
```

**Detection Rules:**

1. **test_type inference:**
   - File in `/tests/` or `/integration/` directory -> `'integration'`
   - File in `/e2e/` or `/cypress/` directory -> `'e2e'`
   - File with `.spec.` or `.test.` in name in same dir as source -> `'unit'`
   - Rust `#[cfg(test)]` module -> `'unit'`
   - Rust `/tests/` directory -> `'integration'`
   - Contains Given/When/Then patterns -> `'bdd'`

2. **uses_mocks inference:**
   - Contains `jest.mock()`, `jest.fn()`, `jest.spyOn()` -> true
   - Uses `mockall` crate (Rust) -> true
   - Contains `@Mock`, `@InjectMocks` annotations -> true
   - Contains `unittest.mock`, `pytest-mock` -> true

### 3. Test Suite Structure

```typescript
interface CASTestSuite {
  id: string;
  name: string;
  file_path: string;
  test_type: 'unit' | 'integration' | 'e2e' | 'acceptance';
  framework: string;

  tests: CASTestCase[];
  hooks: CASTestHook[];
  fixtures: string[];  // Node IDs of fixture/factory nodes
  mocks: string[];     // Node IDs of mock nodes

  coverage?: {
    nodes_tested: string[];  // Node IDs this suite tests
    coverage_percentage?: number;
  };

  metadata?: {
    parallel: boolean;
    timeout_ms?: number;
    retries?: number;
    skip_reason?: string;
  };
}

interface CASTestCase {
  id: string;
  name: string;
  description?: string;
  test_type: 'unit' | 'integration' | 'e2e' | 'acceptance' | 'bdd';

  assertions: CASAssertion[];
  mocks_used: string[];  // Node IDs
  targets: string[];     // Node IDs of code being tested

  bdd_steps?: Array<{
    type: 'given' | 'when' | 'then' | 'and' | 'but';
    text: string;
    implementation_id?: string;
  }>;

  parameterized?: {
    parameters: Array<{ name: string; values: any[] }>;
    case_count: number;
  };

  status: {
    skipped: boolean;
    focused: boolean;  // it.only, test.only, #[ignore] reversed
    flaky: boolean;
  };
}

interface CASTestHook {
  id: string;
  type: 'before_all' | 'before_each' | 'after_each' | 'after_all';
  name?: string;
  node_id: string;
}

interface CASAssertion {
  id: string;
  type: 'equality' | 'truthiness' | 'exception' | 'mock_call' |
        'snapshot' | 'property' | 'custom';
  expression: string;
  target_node?: string;  // What is being asserted about
  location: {
    line: number;
    column?: number;
  };
}
```

### 4. Test-to-Code Edge Types

```typescript
type TestEdgeTypes =
  | 'tests'       // Test -> Code being tested
  | 'mocks'       // Test -> Mock node
  | 'stubs'       // Test -> Stub node
  | 'covers'      // Test -> Covered node (from coverage data)
  | 'validates';  // Assertion -> Validated behavior

interface CASEdge {
  // ...existing fields...

  test_relationship?: {
    assertion_count?: number;
    coverage_contribution?: number;
    mock_type?: 'full' | 'partial' | 'spy';
  };
}
```

**Semantic Rules:**

1. When test calls `userService.createUser()`, create:
   - `tests` edge: test node -> `function_user_service_create_user`

2. When test uses `jest.mock('./userRepository')`, create:
   - `mocks` edge: test node -> mock node
   - Mock node has `target_node` pointing to what it replaces

3. When coverage data shows test covers function:
   - `covers` edge: test node -> covered function node

## Success Criteria

1. **Test Entry Point Type**: All tests use `type: 'test'` (0 tests as events)
2. **Test Categorization**: Tests correctly categorized by type (unit: X, integration: Y, e2e: Z)
3. **Test-to-Code Edges**: Every test has at least one `tests` edge to code it tests
4. **Mock Linking**: Mocks have `target_node` pointing to what they replace
5. **BDD Support**: Tests with Given/When/Then have `bdd_steps` extracted
6. **Coverage Integration**: Nodes show `test_coverage` with `tested_by` references
7. **Test Summary**: `test_summary` accurately reflects test distribution

## Migration from v1.5.0

### Backward Compatibility

- All v1.5.0 outputs remain valid
- New fields are optional
- Existing edges retain their semantics
- Test suites, mocks, fixtures are additive

### Required Updates

1. Update `cas_version` to "1.6.0"
2. Migrate test entry points from `type: 'event'` to `type: 'test'`
3. Run re-analysis to generate test metadata and relationships

### Breaking Changes

- Tests previously marked as `type: 'event'` will now be `type: 'test'`
- Frontend code filtering by `type === 'event'` to find tests must update to `type === 'test'`

## Conclusion

CAS v1.6.0 provides first-class support for test representation and visualization. By adding:

- Dedicated `'test'` entry point type
- Rich test categorization metadata
- Test-to-code relationship edges
- BDD step extraction
- Mock and fixture tracking
- Per-node coverage data
- Test summary statistics

The specification enables comprehensive test visualization including:

- Test areas grouped by domain/module
- Drill-down from "Users" to "User Tests"
- Filter by test type (unit/integration/e2e)
- View BDD scenarios in readable format
- See which code is tested and by what
- Identify coverage gaps
- Track mock usage and what they substitute

This transforms test data from a flat list into an explorable, relationship-rich view that matches the existing API domain visualization pattern.
