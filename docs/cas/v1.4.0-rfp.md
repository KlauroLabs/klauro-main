# CAS v1.4.0 Request for Proposal - Documentation & Comment Extraction

**Version:** 1.4.0 RFP
**Status:** Draft
**Created:** 2025-09-20
**Supersedes:** v1.3.0

## Executive Summary

This RFP proposes CAS v1.4.0 to add comprehensive documentation and comment extraction capabilities across all language and framework analyzers. The enhancement enables complete code context understanding without requiring direct code implementation reading, supporting AI-powered analysis, documentation generation, and knowledge transfer scenarios.

## Problem Statement

### Current Limitations

CAS v1.2.0 and the proposed v1.3.0 lack critical documentation extraction capabilities:

1. **Documentation Loss**: JSDoc, JavaDoc, XML Doc, Python docstrings, and other structured documentation is not captured
2. **Missing Context**: Inline comments explaining complex logic are ignored
3. **Implementation Status Unknown**: No tracking of TODO, FIXME, HACK, or stub markers
4. **Parameter Documentation Lost**: Function parameter descriptions and type hints not preserved
5. **Business Logic Undocumented**: Comments explaining business rules and decisions are missing
6. **Framework Documentation Ignored**: Swagger descriptions, GraphQL schema docs not captured
7. **Code Quality Indicators Missing**: No extraction of deprecation notices, warnings, or implementation notes

### User Impact

Without documentation extraction:
- AI assistants lack crucial context for understanding code intent
- New developers miss important implementation notes and warnings
- Technical debt markers (TODO/FIXME) remain hidden
- API documentation must be separately maintained
- Code review context and decisions are lost
- Business logic explanations are inaccessible

### Vision Alignment

Per CLAUDE.md requirements:
> "I want to package an entire codebase into a package of information that could be used to inform something like claude code... so that claude code can work on a system with ALL of the context it needs without needing to read every file"

Documentation and comments ARE the context. They explain the "why" behind the "what" and are essential for complete understanding.

## Proposed Solution

### Core Schema Enhancements

#### 1. Enhanced CASNode with Documentation

```typescript
interface CASNode {
  // ... existing fields from v1.3.0 ...

  // NEW in v1.4.0
  documentation?: CASDocumentation;
  comments?: CASComment[];
  implementation_status?: CASImplementationStatus;
  todos?: CASTodo[];
}

interface CASDocumentation {
  type: 'jsdoc' | 'javadoc' | 'xmldoc' | 'docstring' | 'rustdoc' | 'godoc' | 'phpdoc' | 'typedoc' | 'other';
  raw: string;
  summary?: string;
  description?: string;

  parameters?: Array<{
    name: string;
    type?: string;
    description?: string;
    optional?: boolean;
    default_value?: string;
  }>;

  returns?: {
    type?: string;
    description?: string;
  };

  throws?: Array<{
    type?: string;
    description?: string;
  }>;

  examples?: Array<{
    title?: string;
    code: string;
    language?: string;
  }>;

  tags?: Array<{
    tag: string;  // @deprecated, @since, @author, @see, @link
    value: string;
    metadata?: Record<string, any>;
  }>;

  framework_docs?: {
    swagger?: {
      summary?: string;
      description?: string;
      tags?: string[];
      operation_id?: string;
    };
    graphql?: {
      description?: string;
      deprecated?: boolean;
      deprecation_reason?: string;
    };
  };

  location: {
    start_line: number;
    end_line: number;
  };
}

interface CASComment {
  id: string;
  type: 'single-line' | 'multi-line' | 'inline' | 'block';
  style: '//' | '#' | '--' | '/* */' | '<!-- -->' | 'other';
  text: string;
  purpose?: 'explanation' | 'todo' | 'warning' | 'note' | 'hack' | 'clarification' | 'disabled-code' | 'other';

  location: {
    file: string;
    line: number;
    column?: number;
    relative_to?: 'above' | 'inline' | 'below';
  };

  context?: {
    preceding_code?: string;
    following_code?: string;
    scope?: string;  // function, class, module, etc.
    scope_id?: string;  // Reference to CASNode
  };

  markers?: {
    is_todo?: boolean;
    is_fixme?: boolean;
    is_hack?: boolean;
    is_warning?: boolean;
    is_note?: boolean;
    is_question?: boolean;
    is_important?: boolean;
    custom_markers?: string[];
  };
}

interface CASTodo {
  id: string;
  type: 'TODO' | 'FIXME' | 'HACK' | 'NOTE' | 'WARNING' | 'XXX' | 'OPTIMIZE' | 'REFACTOR';
  text: string;
  priority?: 'low' | 'medium' | 'high' | 'critical';

  assignee?: string;  // Extracted from TODO(username)
  created_date?: string;  // If specified in comment
  due_date?: string;  // If specified

  location: {
    file: string;
    line: number;
    node_id?: string;  // Associated CASNode
  };

  context?: {
    function_name?: string;
    class_name?: string;
    estimated_effort?: string;
    related_issue?: string;  // GitHub/JIRA issue reference
  };

  classification?: {
    category?: 'bug' | 'feature' | 'refactor' | 'performance' | 'security' | 'documentation' | 'test';
    technical_debt?: boolean;
    blocking?: boolean;
  };
}

interface CASImplementationStatus {
  status: 'complete' | 'partial' | 'stub' | 'not-implemented' | 'deprecated' | 'experimental';

  indicators: {
    has_todo_markers: boolean;
    has_not_implemented_exceptions: boolean;
    has_stub_returns: boolean;
    has_placeholder_code: boolean;
    has_hardcoded_values: boolean;
    has_commented_out_code: boolean;
  };

  completeness?: {
    estimated_percentage?: number;
    missing_features?: string[];
    implemented_features?: string[];
  };

  deprecation?: {
    is_deprecated: boolean;
    deprecated_since?: string;
    removal_version?: string;
    alternative?: string;
    migration_guide?: string;
  };

  experimental?: {
    is_experimental: boolean;
    stability_level?: 'unstable' | 'experimental' | 'beta' | 'stable';
    api_may_change?: boolean;
  };
}
```

    }
  },
  // ... patterns for Java, C#, Go, Rust, PHP, etc.

## Implementation Requirements by Analyzer

### Language Analyzers

#### TypeScript/JavaScript Analyzer
- Extract JSDoc comments with full tag parsing
- Capture TypeDoc-specific annotations
- Parse inline type comments (`// @ts-ignore`, etc.)
- Extract TODO/FIXME with assignee parsing
- Identify stub implementations (throw new Error('Not implemented'))

#### Python Analyzer
- Parse docstrings (Google, NumPy, Sphinx styles)
- Extract type hints from comments
- Capture `# type:` comments
- Identify `raise NotImplementedError()`
- Parse TODO comments with priority indicators

#### Java Analyzer
- Full JavaDoc parsing with all tags
- Extract Spring annotations documentation
- Parse inline implementation notes
- Identify `// NOSONAR` and similar markers
- Capture `@Deprecated` annotations with metadata

#### C# Analyzer
- XML documentation comment parsing
- Extract `/// <summary>`, `/// <param>`, etc.
- Parse `#region` directives as structural comments
- Capture `[Obsolete]` attributes
- Identify `throw new NotImplementedException()`

#### Go Analyzer
- GoDoc comment extraction
- Parse `// Package` documentation
- Extract `// BUG()` comments
- Capture build tags and constraints
- Identify `panic("unimplemented")`

#### Rust Analyzer
- RustDoc comment parsing (`///` and `//!`)
- Extract `#[deprecated]` attributes
- Parse `todo!()`, `unimplemented!()` macros
- Capture `// Safety:` comments
- Identify `unreachable!()` usage

#### PHP Analyzer
- PHPDoc block parsing
- Extract `@param`, `@return`, `@throws`
- Parse Laravel/Symfony documentation patterns
- Capture `// @codeCoverageIgnore`
- Identify `throw new \Exception('Not implemented')`

### Framework Analyzers

#### NestJS Analyzer
- Extract Swagger decorator descriptions
- Parse `@ApiProperty()` documentation
- Capture guard/interceptor documentation
- Extract validation messages as documentation

#### React Analyzer
- Parse component PropTypes comments
- Extract Storybook documentation
- Capture hook dependency comments
- Parse JSX comments

#### Express Analyzer
- Extract route documentation comments
- Parse middleware documentation
- Capture API endpoint descriptions

#### Spring Boot Analyzer
- Parse `@ApiOperation` Swagger annotations
- Extract `@RequestMapping` descriptions
- Capture JavaDoc on controllers/services

#### Django Analyzer
- Parse model field `help_text`
- Extract view docstrings
- Capture admin customization docs

## Impact Analysis

### Benefits
1. **Complete Context**: AI assistants have full understanding without code reading
2. **Knowledge Preservation**: Developer intent and decisions captured
3. **Technical Debt Visibility**: All TODOs and incomplete work surfaced
4. **Quality Metrics**: Documentation coverage measurable
5. **Onboarding Acceleration**: New developers understand "why" not just "what"

### Performance Considerations
- Documentation extraction adds ~10-15% to analysis time
- Additional memory usage for storing comments (~5-10% increase)
- Larger CAS output files (~20-30% increase)
- Optimizations: lazy loading, compression, selective extraction

### Storage Requirements
- Documentation strings average 200-500 bytes per documented node
- Comments average 50-100 bytes each
- TODO items average 100-200 bytes each
- Total increase: ~25-35% of current CAS output size
