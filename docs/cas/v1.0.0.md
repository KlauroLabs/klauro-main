# Code Analysis Specification (CAS) v1.0

## Purpose

The Code Analysis Specification (CAS) defines a flexible, language-agnostic format for representing the complete analysis of any software system. This specification captures every analyzable aspect of a codebase in a structured format that can be consumed by any tool or platform.

This specification is designed to:
- Synthesize an entire codebase into a comprehensive context document
- Enable tools like MCP servers to understand complete system architecture without reading every file
- Support progressive disclosure through hierarchical levels (n levels, determined by analyzer)
- Enable infinite drill-down navigation from system level to individual variables
- Support multiple analyzer contributions (language + framework + library analyzers)
- Capture all relationships, behaviors, and patterns in a system
- Link multiple repositories and external services
- Include package management, dependencies, and library usage
- Track code coverage, testing, and quality metrics
- Be extensible and adaptable to any system architecture

**Key Principles**:
1. **Flexibility First**: The spec is intentionally flexible. Required fields are minimal (id, name, type).
2. **Analyzer-Driven Levels**: Analyzers determine the appropriate number of hierarchical levels.
3. **Progressive Disclosure**: Consumers can request specific levels to avoid loading unnecessary detail.
4. **Complete Synthesis**: Every analyzable aspect should be captured, from system architecture to individual variables.

## Node Structure

Every analyzable element in the system is a node. Nodes form a graph representing the complete system structure. The only truly required fields are `id`, `name`, and `type`. Everything else can be adapted to the specific needs of the system being analyzed.

**Progressive Disclosure**: Nodes are organized in hierarchical levels (n levels, determined by the analyzer). Common patterns include system → architectural → code → members → implementation, but analyzers can define as many or as few levels as appropriate for the codebase. Consumers can query specific levels and drill down as needed.

## Node Categories and Levels

Categories define the hierarchical organization of nodes. Each level represents a different granularity of analysis. The number and naming of levels is flexible and determined by the analyzers based on the system being analyzed.

## Analyzer Collaboration and Coordination

Multiple analyzers work together to create a unified, enriched analysis. Rather than each analyzer creating separate nodes, analyzers collaborate to enhance and hydrate existing nodes with additional metadata and relationships.

### Collaboration Principles

1. **Node Enhancement vs. Creation**: Framework and library analyzers should enhance existing nodes created by language analyzers rather than creating duplicate nodes
2. **ID Consistency**: Analyzers must use compatible ID generation strategies to enable proper node merging
3. **Metadata Enrichment**: Specialized analyzers add framework-specific metadata to base language nodes
4. **Relationship Augmentation**: Framework analyzers add specialized edges (routes, decorators, lifecycle) to existing structural relationships
5. **Orchestrated Merging**: The orchestrator merges analyzer outputs using matching node IDs and compatible metadata

### Example Collaboration Flow

For a NestJS TypeScript application:

1. **TypeScript Analyzer** (Language-level):
   - Creates foundational nodes: classes, methods, properties, interfaces
   - Establishes basic structural relationships: inheritance, imports, calls
   - Provides AST-level metadata: parameters, return types, visibility

2. **NestJS Analyzer** (Framework-level):
   - Finds existing TypeScript class nodes by file path and class name
   - Enhances controller classes with: routes, HTTP methods, decorators, guards
   - Enhances service classes with: injection metadata, provider information
   - Adds framework-specific edges: dependency injection, route mappings
   - Creates entry points for endpoints that reference the enhanced controller method nodes

3. **MikroORM Analyzer** (Library-level):
   - Finds existing TypeScript class nodes representing entities
   - Enhances entity classes with: table mappings, column metadata, relationships
   - Adds database-specific edges: foreign keys, indexes, constraints
   - Creates exit points for database operations that reference enhanced repository method nodes

### Node Enhancement Strategy

```typescript
// Instead of creating new nodes:
const controllerId = generateId('controller', filePath, className); // Creates separate node

// Enhance existing TypeScript class nodes:
const existingClassNode = findNodeByPath(filePath, className);
if (existingClassNode) {
  existingClassNode.subcategories = [...(existingClassNode.subcategories || []), 'controller'];
  existingClassNode.metadata.nestjs = {
    type: 'controller',
    route: '/users',
    guards: ['AuthGuard'],
    decorators: ['@Controller("users")']
  };
}
```

### ID Matching Strategy

Analyzers must use compatible ID generation to enable merging:

```typescript
// Base ID for TypeScript class (created by TypeScript analyzer)
const typeScriptClassId = generateNodeId('class', filePath, className);

// Framework analyzer references the same ID
const enhancedNode = {
  id: typeScriptClassId, // Same ID for merging
  // Enhancement metadata
  metadata: {
    ...existingMetadata,
    nestjs: { /* framework-specific data */ }
  }
};
```

### Orchestrator Merge Logic

The orchestrator combines analyzer outputs using this strategy:

1. **Primary Nodes**: Language analyzers create the foundational node structure
2. **Enhancement Layers**: Framework/library analyzers provide enhancement data
3. **Merge Rules**:
   - Same ID → merge metadata, combine subcategories, union arrays
   - Conflict resolution: specialized analyzer metadata takes precedence
   - Edge deduplication: combine weights, preserve unique relationship types
4. **Reference Integrity**: Entry/exit points reference the final merged node IDs

### Best Practices for Analyzer Developers

1. **Language Analyzers**: Create comprehensive foundational nodes with file locations and basic metadata
2. **Framework Analyzers**: Look up existing nodes by file path and name, enhance rather than duplicate
3. **Library Analyzers**: Focus on usage patterns and enhance nodes that use the library
4. **ID Consistency**: Use standardized ID generation that enables cross-analyzer matching
5. **Graceful Degradation**: Handle cases where expected base nodes don't exist
6. **Documentation**: Clearly document which base analyzer outputs are required

This collaboration approach ensures that the final CAS output represents a unified, comprehensive view of the system where each code element is enriched with all relevant language, framework, and library-specific information.

## ID Generation Strategy

Recommended ID format for consistency across analyzers:

```javascript
function generateId(type, filePath, name) {
  // Normalize path: remove special chars, lowercase
  const normalizedPath = filePath
    .replace(/[^a-zA-Z0-9]/g, '_')
    .toLowerCase()
    .substring(0, 50);

  // Normalize name: remove special chars, keep case
  const normalizedName = name
    .replace(/[^a-zA-Z0-9_]/g, '_')
    .substring(0, 50);

  // Format: type_path_name_hash
  const baseId = `${type}_${normalizedPath}_${normalizedName}`;
  const hash = sha256(filePath + name).substring(0, 8);

  return `${baseId}_${hash}`;
}

// Examples:
// "controller_src_controllers_user_controller_ts_UserController_a3f2d8e1"
// "function_src_services_auth_service_ts_validateToken_b7c9f0a2"
// "component_src_components_dashboard_tsx_Dashboard_d5e1c3b4"
```

## Merge Conflict Resolution

When merging outputs from multiple analyzers:

1. **Node Conflicts**:
   - Same ID → merge metadata, prefer specialized analyzer
   - Priority: framework-specific > language-specific > generic

2. **Edge Conflicts**:
   - Same source+target+type → increase weight/confidence
   - Different types → keep both edges

3. **Metadata Conflicts**:
   - Numeric values → average or max based on type
   - Boolean values → OR operation
   - String values → prefer non-null, then specialized

4. **Category Conflicts**:
   - Keep most specific categorization
   - Maintain all subcategories

## Analyzer Requirements

Requirements for analyzers implementing this specification.

### Minimum Requirements
1. **Node Creation**: Must create nodes for all analyzable elements with id, name, type
2. **Edge Detection**: Must detect and create edges for relationships
3. **Categorization**: Must assign appropriate categories and levels (n levels as appropriate)
4. **Location Tracking**: Must track file locations for all nodes
5. **Parent-Child**: Must maintain parent-child relationships
6. **Entry/Exit Points**: Must identify system boundaries and link to source nodes
7. **Progressive Structure**: Must organize nodes into hierarchical levels (minimum 2 levels)
8. **Analyzer Metadata**: Must identify which analyzer contributed each element
9. **Level Flexibility**: Must define appropriate number of levels based on system complexity

### Recommended Features
1. **Behavior Detection**: Identify and document system behaviors
2. **Pattern Recognition**: Detect common patterns and anti-patterns
3. **Complexity Analysis**: Calculate complexity metrics
4. **Documentation Extraction**: Extract comments and documentation
5. **External Service Detection**: Identify third-party integrations
6. **Security Context**: Identify authentication/authorization boundaries
7. **Test Mapping**: Link tests to tested code
8. **Cross-Repository**: Detect shared dependencies
9. **Library Analysis**: Catalog dependencies and usage patterns
10. **Description Generation**: Provide human-readable descriptions for all elements
11. **Multiple Analyzer Coordination**: Work with other analyzers without conflicts

### Quality Standards
1. **Completeness**: Capture all significant code elements
2. **Accuracy**: Relationships must be verified
3. **Performance**: Analysis should complete in reasonable time
4. **Determinism**: Same code produces same analysis
5. **Incrementality**: Support incremental updates
6. **Error Recovery**: Gracefully handle parsing errors

## Level System Philosophy

The specification supports n-levels of hierarchical organization, not a fixed 5-level system. This flexibility is crucial because:

1. **System Diversity**: A simple CLI tool might only need 3 levels, while a complex enterprise system might need 8+
2. **Framework Specificity**: Different frameworks naturally organize at different depths
3. **Future Proofing**: New languages and patterns shouldn't be constrained by fixed levels
4. **Analyzer Autonomy**: Each analyzer knows best how to organize its domain

### Level Guidelines

- **Minimum**: 2 levels (at least system and implementation)
- **Common Range**: 3-7 levels for most systems
- **Maximum**: No limit - determined by system complexity
- **Naming**: Levels can use standard names (system, architectural, code) or custom names
- **Consistency**: All nodes must have a level for progressive disclosure to work

### Example Level Structures

**Simple Python Script** (3 levels):
1. Script (system)
2. Functions (code)
3. Variables (implementation)

**React + NestJS Application** (5 levels):
1. Applications (frontend, backend)
2. Architectural (controllers, components, services)
3. Code Elements (classes, functions)
4. Members (methods, props)
5. Implementation (variables, statements)

**Microservices Platform** (7 levels):
1. Platform
2. Services
3. Architectural Components
4. Code Elements
5. Members
6. Implementation
7. AST Details

## Summary

The Code Analysis Specification provides a complete, flexible format for synthesizing entire codebases into consumable context documents. With n-level progressive disclosure, multiple analyzer support, and minimal required fields, it enables AI tools, documentation systems, and visualization platforms to understand any codebase without reading every file.

**Core Value Proposition**: Transform 100k+ lines of code into a single, queryable context that AI assistants can progressively explore, making them 10-20x more efficient while providing complete understanding.
