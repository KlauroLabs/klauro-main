# CAS v1.7.0 Request for Proposal - Inference-Based Intelligence

**Version:** 1.7.0 RFP
**Status:** Draft
**Created:** 2026-01-25
**Supersedes:** v1.6.0

## Executive Summary

This RFP proposes CAS v1.7.0 to add eight inference-based intelligence capabilities. All capabilities derive insights **solely** from:
- Static code analysis
- Repository metadata (commits, PRs, blame)
- Runtime SDK telemetry (traffic, latency, errors)

**No external documentation. No manual annotations required.**

## Problem Statement

### Current Limitations (v1.6.0)

1. **No Intent Understanding**: CAS captures WHAT code does but not WHY it exists. Cannot answer "Why was this implemented this way?"

2. **No Flow Criticality**: Call chains exist but lack business criticality signals. Cannot answer "Which flows are most important to the business?"

3. **No Change Risk Assessment**: No per-node risk analysis. Cannot answer "What could break if I change this function?"

4. **No Entity-Centric Data View**: `dataFlow` fields exist but are not entity-centric. Cannot answer "Show me everywhere User data is touched."

5. **No Trust Boundaries**: Entry point security exists but no system-wide trust model. Cannot answer "Where does untrusted input become trusted?"

6. **No Flow-Level Test Coverage**: Per-node coverage exists but not per-flow. Cannot answer "Is this critical user journey fully tested?"

7. **No Temporal Stability**: API stability exists but no code churn analysis. Cannot answer "Is this area stable or constantly changing?"

### User Impact

- Developers cannot understand WHY code exists without reading commit history manually
- Cannot prioritize which changes are risky vs safe
- Cannot see data flow from entry to exit
- Cannot identify security gaps at trust boundaries
- Cannot assess test coverage at the flow level
- Cannot identify volatile/fragile areas of the codebase

### Root Cause

CAS lacks inference layers that synthesize insights from:
- Raw analysis data (comments, TODOs, patterns)
- Git history (commits, blame, PRs)
- Runtime telemetry (traffic, errors, latency)

## Proposed Solution

### Overlap Analysis

Before defining v1.7.0 structures, existing CAS structures were analyzed to avoid duplication:

| Capability | Existing Structures | Recommendation |
|------------|---------------------|----------------|
| Intent Inference | `CASComment`, `CASTodo`, `CASImplementationStatus` | ADD inference layer |
| Critical Flows | `CASCallChain` with `chain_type`, `business_context`, `risk_analysis` | **ENHANCE** existing |
| Change Risk | `CASCallChain.risk_analysis`, `CASImplementationHealth.risk_areas` | NEW per-node structure |
| Data Lifecycle | `CASNode.dataFlow`, `CASEdge.dataFlow` | NEW entity-centric model |
| Security Boundaries | `EntryPoint.security`, `CASDecorator.security_info` | NEW boundary/trust model |
| Flow-Test Coverage | `CASTestCoverage`, `CASTestSuite.coverage` | EXTEND to flow level |
| Temporal Stability | `CASImplementationStatus.experimental.stability_level` | NEW git-based metrics |

## 1. Intent Inference (CASIntent)

**Purpose:** Explain WHY code exists. Synthesize purpose from multiple evidence sources.

**Builds on:** `CASComment`, `CASTodo`, `CASDocumentation`, `CASImplementationStatus`

### Data Structures

```typescript
interface CASIntent {
  node_id: string;
  inferred_purpose?: string;
  inferred_constraints?: string[];
  architectural_decision?: {
    decision: string;
    rationale?: string;
    evidence: IntentEvidence[];
  };
  workaround_indicator?: {
    is_workaround: boolean;
    workaround_for?: string;
    expected_resolution?: string;
  };
  confidence: 'high' | 'medium' | 'low';
}

interface IntentEvidence {
  type: 'commit_message' | 'pr_description' | 'code_comment' |
        'pattern_deviation' | 'naming_convention';
  source: string;
  excerpt: string;
  confidence_contribution: number;
}
```

### Inference Sources

| Source | Evidence Type | Example Signals |
|--------|---------------|-----------------|
| Commit messages | `commit_message` | "hack", "temporary", "workaround", "legacy" |
| PR descriptions | `pr_description` | "because", "due to", "required for" |
| Code comments | `code_comment` | `CASComment.purpose: 'explanation'`, `markers.is_hack` |
| Pattern deviations | `pattern_deviation` | Deviation from detected pattern with no obvious reason |
| Naming conventions | `naming_convention` | "Legacy", "Temp", "V2", "Deprecated" in names |

### Semantic Rules

**Rule 5.15 - Intent Inference:**
- Intent SHOULD be inferred from commit history, comments, and pattern deviations
- Workaround indicators MUST include `confidence` level
- Evidence MUST include `source` references (file path, commit SHA, or PR number)
- When multiple evidence sources agree, confidence SHOULD be `'high'`
- When evidence is from comments only, confidence SHOULD be `'medium'`
- When inferred from naming alone, confidence SHOULD be `'low'`

### Example

```json
{
  "intents": [
    {
      "node_id": "function_rate_limiter_check",
      "inferred_purpose": "Prevents API abuse by limiting request frequency",
      "inferred_constraints": ["Must handle concurrent requests", "Must not block legitimate users"],
      "workaround_indicator": {
        "is_workaround": true,
        "workaround_for": "Third-party API rate limiting",
        "expected_resolution": "Remove when API v2 with higher limits is available"
      },
      "confidence": "high"
    }
  ]
}
```

## 2. Critical Flows - CASCallChain Enhancements

**Purpose:** Identify system's core user journeys with criticality signals.

**Implementation:** ENHANCE existing `CASCallChain` (do NOT create duplicate structure).

### CASCallChain Enhancements (v1.7.0)

```typescript
interface CASCallChain {
  // ... existing v1.3.0 fields ...

  // v1.7.0 ADDITIONS:
  criticality?: 'critical' | 'high' | 'medium' | 'low';
  criticality_factors?: string[];

  runtime_stats?: {
    traffic_volume: 'very-high' | 'high' | 'medium' | 'low';
    avg_latency_ms?: number;
    error_rate_percent?: number;
    last_observed?: string;
  };

  test_coverage?: {
    covered: boolean;
    coverage_percentage?: number;
    test_ids?: string[];
    gaps?: string[];
  };
}
```

### New Top-Level Summary

```typescript
interface CASFlowSummary {
  total_critical_flows: number;
  by_criticality: Record<string, number>;
  untested_critical_flows: string[];
  high_error_rate_flows: string[];
}
```

### Criticality Inference

| Factor | Signal | Criticality Impact |
|--------|--------|-------------------|
| Traffic volume | SDK telemetry | very-high traffic -> critical |
| Error rate | SDK telemetry | high errors + high traffic -> critical |
| Business context | `business_context.business_process` | "Payment", "Auth" -> critical |
| Entry point type | HTTP POST to sensitive endpoint | -> high |
| External dependencies | Payment, notification services | -> high |

### Semantic Rules

**Rule 5.16 - Flow Criticality (extends 5.4):**
- Call chains SHOULD have `criticality` set based on traffic, error rate, and business impact
- `criticality: 'critical'` MUST be assigned when ANY of:
  - `runtime_stats.traffic_volume` is `'very-high'`
  - `runtime_stats.error_rate_percent` > 5 AND traffic is high
  - `business_context.business_process` contains "payment", "auth", or "checkout"
- `runtime_stats` SHOULD be populated when SDK telemetry is available
- `test_coverage.test_ids` MUST reference existing test entry point IDs
- `test_coverage.gaps` SHOULD list node IDs of untested segments

### Example

```json
{
  "call_chains": [
    {
      "id": "chain_checkout_flow",
      "chain_type": "critical-path",
      "criticality": "critical",
      "criticality_factors": ["High traffic", "Revenue impacting", "Payment processing"],
      "runtime_stats": {
        "traffic_volume": "very-high",
        "avg_latency_ms": 245,
        "error_rate_percent": 0.3,
        "last_observed": "2026-01-25T10:00:00Z"
      },
      "test_coverage": {
        "covered": true,
        "coverage_percentage": 85,
        "test_ids": ["test_checkout_happy_path", "test_checkout_payment_failure"],
        "gaps": ["function_handle_refund"]
      },
      "entry_point": { "node_id": "controller_checkout_submit", "method_name": "submit" },
      "call_path": [...]
    }
  ],
  "flow_summary": {
    "total_critical_flows": 5,
    "by_criticality": { "critical": 5, "high": 12, "medium": 34, "low": 89 },
    "untested_critical_flows": ["chain_password_reset"],
    "high_error_rate_flows": []
  }
}
```

## 3. Change Impact/Risk (CASChangeRisk)

**Purpose:** Assess what could break if a node is modified.

**Distinct from:** `CASCallChain.risk_analysis` (execution risk). This is per-node CHANGE risk.

### Data Structures

```typescript
interface CASChangeRisk {
  node_id: string;
  risk_level: 'critical' | 'high' | 'medium' | 'low';
  risk_factors: ChangeRiskFactor[];

  downstream_impact: {
    direct_callers: string[];
    transitive_callers: string[];
    affected_call_chains: string[];
    affected_entry_points: string[];
  };

  test_protection: {
    has_direct_tests: boolean;
    has_integration_tests: boolean;
    test_ids?: string[];
    untested_callers?: string[];
  };

  stability_context: {
    recent_churn: boolean;
    commit_count_30d: number;
    bug_fix_density: number;
    last_refactor?: string;
  };

  recommendations?: string[];
}

interface ChangeRiskFactor {
  factor: 'many-callers' | 'critical-path' | 'high-traffic' |
          'no-tests' | 'recent-bugs' | 'complex-logic' |
          'external-dependency' | 'security-sensitive';
  severity: 'high' | 'medium' | 'low';
  details: string;
}

interface CASChangeRiskSummary {
  high_risk_nodes: string[];
  untested_critical_paths: string[];
  recent_hotspots: string[];
}
```

### Risk Calculation

| Factor | Severity | Condition |
|--------|----------|-----------|
| `many-callers` | high | > 10 direct callers |
| `critical-path` | high | In call chain with `criticality: 'critical'` |
| `high-traffic` | high | `runtime_stats.traffic_volume: 'very-high'` |
| `no-tests` | high | `test_protection.has_direct_tests: false` |
| `recent-bugs` | high | `stability_context.bug_fix_density` > 0.3 |
| `external-dependency` | medium | Has outgoing edge to `ExitPoint` |
| `security-sensitive` | high | Node has security tags or handles auth |

### Semantic Rules

**Rule 5.17 - Change Risk:**
- Risk level MUST consider: caller count, critical path membership, test coverage, stability
- `risk_level: 'critical'` MUST be assigned when 2+ high-severity factors present
- `downstream_impact.affected_call_chains` MUST reference existing `CASCallChain` IDs
- `stability_context.bug_fix_density` SHOULD be calculated as: (bug fix commits / total commits)
- Bug fix commits SHOULD be identified by commit message patterns: "fix", "bug", "issue", "patch"

### Example

```json
{
  "change_risks": [
    {
      "node_id": "function_user_service_validate",
      "risk_level": "high",
      "risk_factors": [
        { "factor": "many-callers", "severity": "high", "details": "Called by 15 functions" },
        { "factor": "critical-path", "severity": "high", "details": "In checkout and login flows" },
        { "factor": "no-tests", "severity": "high", "details": "No direct test coverage" }
      ],
      "downstream_impact": {
        "direct_callers": ["function_auth_login", "function_checkout_verify", "..."],
        "transitive_callers": ["controller_auth", "controller_checkout", "..."],
        "affected_call_chains": ["chain_login_flow", "chain_checkout_flow"],
        "affected_entry_points": ["entry_post_login", "entry_post_checkout"]
      },
      "test_protection": {
        "has_direct_tests": false,
        "has_integration_tests": true,
        "test_ids": ["test_login_integration"],
        "untested_callers": ["function_checkout_verify"]
      },
      "stability_context": {
        "recent_churn": true,
        "commit_count_30d": 8,
        "bug_fix_density": 0.375,
        "last_refactor": "2026-01-10T00:00:00Z"
      },
      "recommendations": [
        "Add direct unit tests before modifying",
        "Consider impact on checkout flow"
      ]
    }
  ],
  "change_risk_summary": {
    "high_risk_nodes": ["function_user_service_validate", "function_payment_process"],
    "untested_critical_paths": ["chain_password_reset"],
    "recent_hotspots": ["function_user_service_validate"]
  }
}
```

## 4. Data Lifecycle (CASDataEntity)

**Purpose:** Track how data entities flow through the system.

**Distinct from:** `CASNode.dataFlow` (not entity-centric). This models named entities.

### Data Structures

```typescript
interface CASDataEntity {
  id: string;
  name: string;
  schema_source?: string;

  fields?: Array<{
    name: string;
    type: string;
    is_sensitive: boolean;
    validation?: string[];
  }>;

  lifecycle: {
    created_by: string[];
    read_by: string[];
    updated_by: string[];
    deleted_by: string[];
  };

  transformations?: Array<{
    from_node: string;
    to_node: string;
    transformation_type: 'map' | 'filter' | 'aggregate' |
                         'enrich' | 'validate' | 'sanitize';
  }>;

  invariants?: Array<{
    description: string;
    enforced_by: string[];
    source: 'validation' | 'constraint' | 'test' | 'assertion';
  }>;
}

interface CASDataSummary {
  entities: CASDataEntity[];
  sensitive_data_nodes: string[];
  validation_gaps: Array<{
    entity_id: string;
    missing_validation: string;
  }>;
}
```

### Entity Detection

| Source | Detection Method |
|--------|------------------|
| ORM models | MikroORM `@Entity`, TypeORM, Prisma schema |
| Migrations | Database migration files |
| Types/Interfaces | Named types with CRUD methods nearby |
| GraphQL | Type definitions |

### Sensitive Field Detection

Fields SHOULD be marked `is_sensitive: true` when name contains:
- `password`, `secret`, `token`, `key`, `credential`
- `ssn`, `social_security`, `tax_id`
- `email`, `phone`, `address` (PII)
- `card`, `cvv`, `account_number` (payment)

### Semantic Rules

**Rule 5.18 - Data Entity:**
- Entities SHOULD be inferred from schema files, ORM models, and type definitions
- Sensitive fields MUST be flagged based on naming conventions
- `lifecycle` operations MUST map to node IDs that perform CRUD
- `validation_gaps` SHOULD flag entities with `created_by` but no `validation` rules

### Example

```json
{
  "data_entities": [
    {
      "id": "entity_user",
      "name": "User",
      "schema_source": "src/entities/user.entity.ts",
      "fields": [
        { "name": "id", "type": "uuid", "is_sensitive": false },
        { "name": "email", "type": "string", "is_sensitive": true, "validation": ["email format", "unique"] },
        { "name": "password_hash", "type": "string", "is_sensitive": true, "validation": ["min length"] }
      ],
      "lifecycle": {
        "created_by": ["function_user_service_create"],
        "read_by": ["function_user_service_find_by_id", "function_auth_service_validate"],
        "updated_by": ["function_user_service_update", "function_user_service_change_password"],
        "deleted_by": ["function_user_service_delete"]
      },
      "transformations": [
        {
          "from_node": "function_user_service_create",
          "to_node": "function_hash_password",
          "transformation_type": "sanitize"
        }
      ],
      "invariants": [
        { "description": "email must be unique", "enforced_by": ["entity_user"], "source": "constraint" },
        { "description": "password must be hashed", "enforced_by": ["function_hash_password"], "source": "validation" }
      ]
    }
  ],
  "data_summary": {
    "entities": [...],
    "sensitive_data_nodes": ["function_user_service_create", "function_auth_service_validate"],
    "validation_gaps": [
      { "entity_id": "entity_order", "missing_validation": "total_amount has no bounds validation" }
    ]
  }
}
```

## 5. Security Boundaries (CASSecurityBoundary)

**Purpose:** Model where security is enforced and identify trust transitions.

**Builds on:** `EntryPoint.security`, `CASDecorator.security_info`

### Data Structures

```typescript
interface CASSecurityBoundary {
  id: string;
  name: string;
  boundary_type: 'authentication' | 'authorization' | 'input-validation' |
                 'output-encoding' | 'rate-limiting' | 'encryption';

  enforcement_points: Array<{
    node_id: string;
    mechanism: string;
    confidence: 'enforced' | 'assumed' | 'missing';
  }>;

  trust_transition: {
    from_trust_level: 'untrusted' | 'partially-trusted' | 'trusted';
    to_trust_level: 'untrusted' | 'partially-trusted' | 'trusted';
  };

  sensitive_operations: string[];
  bypass_risks?: string[];
}

interface CASSecurityContext {
  node_id: string;
  trust_level: 'untrusted' | 'partially-trusted' | 'trusted';
  security_relevant: boolean;
  security_relevance_reason?: string;
  required_protections: string[];
  actual_protections: string[];
  protection_gaps?: string[];
}

interface CASSecuritySummary {
  boundaries: CASSecurityBoundary[];
  unprotected_sensitive_ops: string[];
  assumed_vs_enforced: {
    enforced: number;
    assumed: number;
    missing: number;
  };
}
```

### Trust Level Propagation

| Node Position | Trust Level |
|---------------|-------------|
| HTTP entry point handler | `untrusted` |
| After auth guard | `partially-trusted` (identity known) |
| After authorization check | `trusted` |
| After input validation | `trusted` for that input |

### Semantic Rules

**Rule 5.19 - Security Boundaries:**
- Boundaries SHOULD be inferred from guards, middleware, and decorators
- Trust levels MUST propagate through the call graph based on boundary crossings
- `confidence: 'enforced'` SHOULD be set when guard/middleware explicitly present
- `confidence: 'assumed'` SHOULD be set when trust is implied but not enforced
- `confidence: 'missing'` MUST be set when sensitive operation lacks protection
- `protection_gaps` MUST be flagged when `required_protections` differs from `actual_protections`

### Example

```json
{
  "security_boundaries": [
    {
      "id": "boundary_auth",
      "name": "Authentication Boundary",
      "boundary_type": "authentication",
      "enforcement_points": [
        { "node_id": "guard_jwt_auth", "mechanism": "JWT validation", "confidence": "enforced" }
      ],
      "trust_transition": {
        "from_trust_level": "untrusted",
        "to_trust_level": "partially-trusted"
      },
      "sensitive_operations": ["function_get_user_profile", "function_update_settings"]
    }
  ],
  "security_contexts": [
    {
      "node_id": "function_get_user_profile",
      "trust_level": "partially-trusted",
      "security_relevant": true,
      "security_relevance_reason": "Returns user PII",
      "required_protections": ["boundary_auth"],
      "actual_protections": ["boundary_auth"],
      "protection_gaps": []
    }
  ],
  "security_summary": {
    "boundaries": [...],
    "unprotected_sensitive_ops": ["function_admin_export"],
    "assumed_vs_enforced": { "enforced": 15, "assumed": 3, "missing": 1 }
  }
}
```

## 6. Flow-Test Coverage (CASFlowCoverage)

**Purpose:** Assess test coverage at the flow level, not just per-node.

**Builds on:** `CASTestCoverage` (per-node), `CASTestSuite.coverage`

### Data Structures

```typescript
interface CASFlowCoverage {
  call_chain_id: string;
  call_chain_name?: string;

  coverage_status: 'fully-covered' | 'partially-covered' | 'not-covered';
  coverage_percentage?: number;

  tested_segments: Array<{
    node_id: string;
    test_ids: string[];
    assertion_count: number;
  }>;

  untested_segments: Array<{
    node_id: string;
    importance: 'critical' | 'high' | 'medium' | 'low';
    reason: string;
  }>;

  test_quality: {
    has_unit_tests: boolean;
    has_integration_tests: boolean;
    has_e2e_tests: boolean;
    uses_mocks: boolean;
    mock_targets?: string[];
  };
}

interface CASTestGap {
  gap_type: 'untested-flow' | 'untested-branch' | 'mock-only' | 'no-assertions';
  location: {
    node_id?: string;
    call_chain_id?: string;
    line?: number;
  };
  severity: 'critical' | 'high' | 'medium' | 'low';
  recommendation: string;
}
```

### Coverage Status Rules

| Status | Condition |
|--------|-----------|
| `fully-covered` | All nodes in flow have tests AND assertions |
| `partially-covered` | Some nodes tested, or mock-only coverage |
| `not-covered` | No tests exercise this flow |

### Semantic Rules

**Rule 5.20 - Flow Coverage:**
- Flow coverage MUST extend existing per-node coverage to `CASCallChain` level
- `coverage_percentage` SHOULD be calculated as: (tested_nodes / total_nodes_in_chain) * 100
- Test gaps MUST be categorized by severity based on `CASCallChain.criticality`
- `gap_type: 'mock-only'` SHOULD be flagged when all tests use mocks for critical dependencies
- `untested_segments[].importance` SHOULD align with the flow's criticality

### Example

```json
{
  "flow_coverage": [
    {
      "call_chain_id": "chain_checkout_flow",
      "call_chain_name": "Checkout Flow",
      "coverage_status": "partially-covered",
      "coverage_percentage": 75,
      "tested_segments": [
        { "node_id": "controller_checkout_submit", "test_ids": ["test_checkout_happy"], "assertion_count": 5 },
        { "node_id": "service_payment_process", "test_ids": ["test_payment_mock"], "assertion_count": 3 }
      ],
      "untested_segments": [
        { "node_id": "service_inventory_reserve", "importance": "high", "reason": "Error handling path" },
        { "node_id": "service_notification_send", "importance": "low", "reason": "Side effect only" }
      ],
      "test_quality": {
        "has_unit_tests": true,
        "has_integration_tests": true,
        "has_e2e_tests": false,
        "uses_mocks": true,
        "mock_targets": ["service_payment_gateway"]
      }
    }
  ],
  "test_gaps": [
    {
      "gap_type": "mock-only",
      "location": { "node_id": "service_payment_process", "call_chain_id": "chain_checkout_flow" },
      "severity": "high",
      "recommendation": "Add integration test with payment sandbox"
    },
    {
      "gap_type": "untested-flow",
      "location": { "call_chain_id": "chain_password_reset" },
      "severity": "critical",
      "recommendation": "Critical flow has no test coverage"
    }
  ]
}
```

## 7. Temporal Stability (CASTemporalStability)

**Purpose:** Identify stable vs volatile vs fragile areas from git history.

**Distinct from:** `CASImplementationStatus.experimental.stability_level` (API stability). This is CODE stability.

### Data Structures

```typescript
interface CASTemporalStability {
  node_id: string;

  stability_score: number;
  stability_class: 'stable' | 'evolving' | 'volatile' | 'fragile';

  churn_metrics: {
    commits_30d: number;
    commits_90d: number;
    unique_authors_30d: number;
    lines_changed_30d: number;
  };

  quality_signals: {
    bug_fix_rate: number;
    refactor_frequency: 'frequent' | 'occasional' | 'rare';
    has_recent_regression: boolean;
  };

  age_context: {
    file_age_days: number;
    last_major_change?: string;
    is_legacy: boolean;
  };

  risk_correlation?: {
    high_churn_high_bugs: boolean;
    recent_refactor_unstable: boolean;
  };
}

interface CASStabilitySummary {
  by_stability_class: Record<string, number>;
  hotspots: Array<{
    node_id: string;
    reason: string;
  }>;
  legacy_areas: string[];
}
```

### Stability Classification

| Class | Criteria |
|-------|----------|
| `stable` | commits_30d <= 2, bug_fix_rate < 0.1, file_age > 180 days |
| `evolving` | commits_30d 3-10, bug_fix_rate < 0.2, active development |
| `volatile` | commits_30d > 10, high churn regardless of bug fixes |
| `fragile` | bug_fix_rate > 0.3, OR high_churn_high_bugs correlation |

### Legacy Detection

Code SHOULD be marked `is_legacy: true` when:
- File age > 2 years AND no commits in 6 months
- Comments contain "legacy", "deprecated", "old"
- `CASImplementationStatus.deprecation.is_deprecated: true`

### Semantic Rules

**Rule 5.21 - Temporal Stability:**
- Stability MUST be calculated from git history (commits, blame)
- `stability_score` SHOULD be 0-100, where 100 is most stable
- Bug fix rate SHOULD be inferred from commit messages containing: "fix", "bug", "patch", "issue"
- `is_legacy` SHOULD be detected from comments containing "legacy", "deprecated", "old"
- `hotspots` MUST be flagged when `stability_class` is `'volatile'` or `'fragile'`
- `risk_correlation.high_churn_high_bugs` MUST be true when commits_30d > 5 AND bug_fix_rate > 0.3

### Example

```json
{
  "temporal_stability": [
    {
      "node_id": "function_user_service_validate",
      "stability_score": 35,
      "stability_class": "fragile",
      "churn_metrics": {
```

## 8. System Capabilities (SystemCapability)

**Purpose:** Group entry points into meaningful capabilities and determine what the system does.

**Builds on:** `EntryPoint`, `CASDataEntity`, `CASCallChain`

### Data Structures

```typescript
interface SystemCapability {
  id: string;
  name: string;
  description: string;
  category: 'core' | 'supporting' | 'admin' | 'internal';

  operations: Array<{
    entry_point_id: string;
    entry_point_type: string;
    action: string;
    path_or_command?: string;
  }>;

  // CLI-specific: For CLI tools, capabilities are implemented by function clusters
  // These are the actual functions that perform the capability, invoked by subcommands
  implementing_functions?: string[];  // Node IDs of functions that implement this capability

  related_entities: string[];
  related_domains: string[];
  criticality: 'critical' | 'high' | 'medium' | 'low';
  criticality_factors: string[];
}

interface SystemPurpose {
  primary_type: string;
  confidence: number;
  evidence: string[];
  secondary_types?: string[];
}
```

### Capability Grouping

Entry points are grouped by resource domain, but the strategy differs significantly by system type:

| Entry Point Type | Grouping Strategy |
|------------------|-------------------|
| HTTP | First path segment after `/api/` |
| CLI | **See CLI-Specific Detection below** |
| Event/Message | Event type or channel |
| Scheduled | "Scheduled Tasks" |
| Page/Route | Route prefix |

#### CLI-Specific Capability Detection

**Critical Distinction:** For CLI tools, entry points (subcommands) do NOT map to capabilities. They represent invocation modes.

**Problem Example:**
A security scanner CLI has subcommands: `quick`, `standard`, `deep`, `stealth`
- These are NOT capabilities - they are scan intensity modes
- The actual capabilities are: "Port Scanning", "Web Enumeration", "Vulnerability Detection", "Service Fingerprinting"
- All subcommands invoke these same capabilities with different parameters

**CLI Capability Detection Strategy:**

1. **Analyze Call Graphs from Entry Points:**
   - Trace what each subcommand calls
   - Identify shared function clusters across subcommands
   - Functions called by 2+ subcommands are likely core capabilities

2. **Semantic Function Clustering:**
   - Group functions by naming patterns (e.g., `scan_*`, `detect_*`, `enumerate_*`)
   - Functions in same module that work together form capability clusters
   - Look for functions that represent complete operations (scan a port, enumerate a service)

3. **Capability Signals:**
   - Functions with exit points (file I/O, network calls) are capability boundaries
   - Functions with high call counts (called by many others) are core utilities, not capabilities
   - Functions that match domain vocabulary (for a scanner: "scan", "detect", "probe") are likely capabilities

4. **Output Structure for CLI Tools:**
   ```json
   {
     "system_capabilities": [
       {
         "id": "cap_port_scanning",
         "name": "Port Scanning",
         "description": "Network port discovery and service detection",
         "category": "core",
         "operations": [
           { "entry_point_id": "ep_quick", "entry_point_type": "cli", "action": "Invoke", "path_or_command": "scan quick" },
           { "entry_point_id": "ep_deep", "entry_point_type": "cli", "action": "Invoke", "path_or_command": "scan deep" }
         ],
         "implementing_functions": ["function_scan_port", "function_probe_service"],
         "criticality": "high"
       }
     ]
   }
   ```

**Note:** For CLI tools, `operations` shows which subcommands invoke the capability, NOT that each operation IS a capability.

### Category Classification

| Category | Criteria |
|----------|----------|
| `core` | Has mutation operations (POST, PUT, DELETE) |
| `supporting` | Read-only operations |
| `admin` | Path contains "admin", "manage", "config" |
| `internal` | Path contains "health", "metrics", "internal" |

### Criticality Scoring (Multi-Signal)

Instead of keyword matching, criticality uses weighted signals:

| Signal | Points | Description |
|--------|--------|-------------|
| Sensitive data | +25 | Related entities have `is_sensitive` fields |
| Auth-related | +20 | Path matches auth patterns |
| Payment-related | +30 | Path matches payment patterns |
| Requires auth | +5 | `authentication.required: true` |
| Has mutations | +10 | POST/PUT/DELETE/PATCH methods |
| Many callers | +1-10 | Called by 5+ other components |
| Admin operations | +15 | Administrative functionality |

**Thresholds:**
- >= 70: critical
- >= 50: high
- >= 25: medium
- < 25: low

### System Purpose Inference

System type is inferred by matching against signatures:

| System Type | Path Patterns | Entity Patterns |
|-------------|---------------|-----------------|
| `e-commerce` | cart, checkout, product, order | product, order, cart |
| `saas-platform` | workspace, organization, tenant | workspace, subscription |
| `content-management` | post, article, content, media | post, article, page |
| `api-service` | api, v1, v2 | - |
| `cli-tool` | - (CLI entry points dominate) | - |
| `authentication-service` | auth, login, oauth, sso | user, session, token |
| `analytics-platform` | analytics, report, dashboard | metric, report, event |

**CLI Tool Detection Signals:**
- Entry points are predominantly `type: 'cli'`
- Has `main` function as primary entry
- Subcommand pattern detected (clap, structopt, argparse, cobra)
- No HTTP/gRPC/GraphQL entry points
- Output primarily to stdout/files rather than network responses

When `cli-tool` is detected, capability detection switches to function-cluster analysis rather than entry-point grouping (see Rule 5.22a).

### Semantic Rules

**Rule 5.22 - System Capabilities:**
- Capabilities SHOULD be grouped by resource domain from entry points
- Criticality MUST use multi-signal scoring, not keyword matching
- `category` SHOULD be inferred from operation types and path patterns
- `related_entities` MUST reference `CASDataEntity` IDs touched by this capability

**Rule 5.22a - CLI-Specific Capability Detection:**
- For CLI tools, entry points (subcommands) represent invocation modes, NOT capabilities
- Capabilities MUST be detected by analyzing function clusters and call graphs
- `implementing_functions` SHOULD list the node IDs of functions that perform the capability
- Multiple subcommands MAY invoke the same capability with different parameters
- Capability names SHOULD reflect the business operation (e.g., "Port Scanning") not the subcommand name (e.g., "Quick Scan")
- Function clustering for CLI capabilities SHOULD consider:
  - Functions called by 2+ entry points (shared core functionality)
  - Functions with exit points (I/O operations indicate capability boundaries)
  - Semantic grouping by function name patterns
  - Module organization (functions in same module often form a capability)

**Rule 5.23 - System Purpose:**
- System type SHOULD be inferred from entry points, entities, and capabilities
- `confidence` MUST be 0.0-1.0 based on evidence match strength
- `secondary_types` SHOULD list other matching system signatures
- CLI-dominated codebases SHOULD be classified as `cli-tool`

## Conclusion

CAS v1.7.0 adds inference-based intelligence capabilities that synthesize insights from:
- Existing analysis data (comments, TODOs, patterns)
- Git history (commits, blame, PRs)
- Runtime telemetry (traffic, errors, latency)

Key design decisions:
1. **ENHANCE `CASCallChain`** for critical flows instead of creating duplicate structure
2. **Build on existing** security, coverage, and documentation structures
3. **Reference existing IDs** (`node_id`, `call_chain_id`) to maintain consistency
4. **All fields optional** for backward compatibility
5. **System-type-aware capability detection**: Entry points map to capabilities for web APIs, but for CLI tools capabilities are detected from function clusters (subcommands are invocation modes, not capabilities)

This enables answering questions like:
- "Why does this code exist?" (Intent)
- "What are the most important flows?" (Critical Flows)
- "What could break if I change this?" (Change Risk)
- "Where does this data go?" (Data Lifecycle)
- "Is this properly secured?" (Security Boundaries)
- "Is this critical flow tested?" (Flow Coverage)
- "Is this area stable or fragile?" (Temporal Stability)
- "What does this system do?" (System Capabilities - with CLI-specific detection)
- "What type of system is this?" (System Purpose)
