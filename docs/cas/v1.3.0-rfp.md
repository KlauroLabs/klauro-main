# CAS v1.3.0 Request for Proposal - Call Graph & Method Invocation Support

**Version:** 1.3.0 RFP
**Status:** Draft
**Created:** 2024-09-20
**Supersedes:** v1.2.0

## Executive Summary

This RFP proposes CAS v1.3.0 to add comprehensive call graph tracking and method invocation analysis capabilities. The current v1.2.0 specification lacks the granular call relationship tracking needed for deep code understanding and navigation.

## Problem Statement

### Current Limitations

CAS v1.2.0 provides entry points, exit points, and basic node relationships, but lacks:

1. **Method Invocation Tracking**: No way to track function-to-function calls with execution context
2. **Call Graph Relationships**: Missing standardized call relationship types and metadata
3. **Decorator/Annotation Semantics**: No framework-specific decorator analysis (NestJS, Spring, etc.)
4. **Abstract Implementation Tracking**: No interface-to-implementation call resolution
5. **Call Context Analysis**: Missing conditional, loop, async, and recursive call patterns
6. **Library Call Granularity**: Exit points lack method-level external call tracking

### User Requirements

From the AnalyzerController.getDetectedAnalyzers example, users need to see:
- HTTP endpoint detection through decorator analysis
- Method call chains: `casAnalyzerService.getDetectedAnalyzers(projectPath)`
- Library exit points: `fs.pathExists()` calls
- Internal method calls: `orchestrator.detectAnalyzers()`
- Recursive patterns: `shouldUseAnalyzer()`, `orderAnalyzers()`
- Abstract implementations: `analyzer.canAnalyze()` from BaseAnalyzer

## Proposed Solution

### New Core Interfaces

#### 1. CASMethodCall

```typescript
interface CASMethodCall {
  id: string;
  caller_node: string;              // Source node ID
  target_node?: string;             // Target node ID (null for external)

  call_details: {
    method_name: string;
    signature?: string;
    location: {
      file: string;
      line: number;
      column: number;
    };
    call_type: 'direct' | 'method' | 'constructor' | 'abstract' | 'interface' | 'callback' | 'hook' | 'dynamic';
    resolution_type: 'static' | 'dynamic' | 'polymorphic' | 'external' | 'unresolved';
  };

  execution_context: {
    is_async: boolean;
    is_conditional: boolean;
    is_in_loop: boolean;
    is_recursive: boolean;
    call_depth: number;
    conditional_depth: number;
    loop_depth: number;
    enclosing_function?: string;
    enclosing_class?: string;
  };

  arguments?: Array<{
    position: number;
    type?: string;
    value?: string;
    is_literal: boolean;
    is_variable: boolean;
  }>;

  external_details?: {
    library: string;
    module?: string;
    is_builtin: boolean;
    is_sdk: boolean;
    exit_point_id?: string;
  };

  framework_semantics?: {
    framework: string;
    decorator_type?: string;
    semantic_meaning?: string;
    route_info?: {
      method: string;
      path: string;
      parameters?: string[];
    };
  };

  performance_hints: {
    is_hot_path: boolean;
    is_potential_bottleneck: boolean;
    estimated_frequency?: number;
    is_critical_path?: boolean;
  };

  metadata?: Record<string, any>;
}
```

#### 2. CASCallChain

```typescript
interface CASCallChain {
  id: string;
  chain_type: 'entry-to-exit' | 'circular' | 'recursive' | 'dead-end' | 'hot-path' | 'critical-path';

  entry_point: {
    node_id: string;
    method_name: string;
    entry_point_id?: string;
  };

  exit_point?: {
    node_id?: string;
    method_name: string;
    exit_point_id?: string;
  };

  call_path: Array<{
    call_id: string;
    node_id: string;
    method_name: string;
    depth: number;
    execution_branch?: string;
  }>;

  characteristics: {
    total_calls: number;
    max_depth: number;
    has_external_calls: boolean;
    has_database_calls: boolean;
    has_async_calls: boolean;
    is_circular: boolean;
    is_recursive: boolean;
    complexity_score: number;
  };

  business_context?: {
    user_action?: string;
    business_process?: string;
    feature_area?: string;
  };

  risk_analysis: {
    risk_level: 'low' | 'medium' | 'high' | 'critical';
    risk_factors: string[];
    bottlenecks?: Array<{
      node_id: string;
      method_name: string;
      reason: string;
      impact: 'low' | 'medium' | 'high';
    }>;
  };

  metadata?: Record<string, any>;
}
```

## Success Criteria

### For AnalyzerController.getDetectedAnalyzers Example

The enhanced CAS should capture:

1. **HTTP Endpoint**: `@Get('detected')` decorator creates entry point
2. **Method Calls**: `casAnalyzerService.getDetectedAnalyzers(projectPath)` tracked as method call
3. **Library Calls**: `fs.pathExists()` tracked as external method call with exit point
4. **Internal Calls**: `orchestrator.detectAnalyzers()` chain fully traced
5. **Recursive Patterns**: `shouldUseAnalyzer()` calls identified with recursion flags
6. **Abstract Implementations**: `analyzer.canAnalyze()` calls resolved to concrete implementations
7. **Complete Call Chain**: Entry-to-exit flow for entire request lifecycle

### General Success Metrics

- 100% method call coverage for analyzed codebases
- Complete call chain reconstruction from entry to exit
- Framework decorator semantic understanding
- Performance bottleneck identification
- Abstract-to-concrete call resolution
