# CAS v1.5.0 Request for Proposal - Class Relationships & Pattern Analysis

**Version:** 1.5.0 RFP
**Status:** Draft
**Created:** 2026-01-09
**Supersedes:** v1.4.0

## Executive Summary

This RFP proposes CAS v1.5.0 to address critical gaps in class-level relationship tracking, pattern variation detection, and framework-specific analysis improvements. The enhancements enable accurate visualization of service dependencies, repository relationships, and architectural patterns without requiring frontend computation.

## Problem Statement

### Current Limitations (v1.4.0)

1. **Class-Level Edges Missing**: Call graph only tracks method-to-method calls. When viewing a class node (e.g., `UserRepository`), "Called By" is empty because edges target methods, not the containing class.

2. **Pattern Variations Not Detected**: CAS detects patterns but not variations (e.g., 30% of repositories use NestJS DI, 70% use manual instantiation).

3. **Controller Base Paths Missing**: Routes show `path: ':id'` instead of full paths like `/workspaces/:id`.

4. **Class-Level Guards Ignored**: All endpoints show `authenticated: false` even when protected by class-level `@UseGuards()`.

5. **Repository Detection Incomplete**: Only repositories with `@Injectable()` are detected; those using manual instantiation are missed.

6. **Class Properties Not Parented**: Property nodes have `parent: null` instead of referencing their containing class.

7. **External Services Noise**: Built-in JS objects (Object, Array, Promise) pollute external services list.

8. **Anonymous Function Edge Orphans**: Edges reference `function_..._anonymous_0` nodes that don't exist.

### User Impact

- Frontend cannot display "Called By" for class-like nodes without computing relationships
- Pattern deviations (inconsistent DI adoption) are invisible
- Authentication status is always wrong for guarded endpoints
- 30-70% of repositories are undetected
- Database schema shows entities with 0 fields

### Root Cause

The CAS spec lacks:
- Class-to-class relationship edge types (`uses`, `depends_on`, `injects`)
- Pattern variation schema
- Full HTTP path requirements for entry points
- Merged guard requirements for authentication

## Proposed Solution

### 1. New Edge Types for Class Relationships

```typescript
type ClassRelationshipEdgeTypes =
  | 'uses'           // ClassA uses ClassB (any method-level call between them)
  | 'depends_on'     // ClassA depends on ClassB (constructor injection)
  | 'instantiates'   // ClassA instantiates ClassB (new ClassB())
  | 'injects';       // ClassA receives ClassB via DI

interface CASEdge {
  // ... existing fields ...

  aggregated_from?: string[];  // For class-level edges: list of method-level call IDs
  relationship_metadata?: {
    injection_type?: 'constructor' | 'property' | 'method';
    instantiation_count?: number;
    usage_locations?: Array<{ file: string; line: number }>;
  };
}
```

**Semantic Rules:**

1. When method `ClassA.foo()` calls `ClassB.bar()`, create BOTH:
   - `calls` edge: `method_ClassA_foo` -> `method_ClassB_bar`
   - `uses` edge: `class_ClassA` -> `class_ClassB` (if not already exists)

2. When constructor receives dependency via DI:
   - `depends_on` edge: `class_ServiceA` -> `class_RepositoryB`
   - `injects` edge: parent module -> `class_ServiceA`

3. When `new ClassName()` is encountered:
   - `instantiates` edge: containing class -> `class_ClassName`

### 2. Pattern Variations Schema

```typescript
interface CASPattern {
  id: string;
  name: string;
  description?: string;
  confidence: number;
  instances: string[];  // Node IDs

  variations?: CASPatternVariation[];
  deviations?: CASPatternDeviation[];
}

interface CASPatternVariation {
  id: string;
  implementation: string;  // 'nestjs-di', 'manual-instantiation', etc.
  description: string;
  instances: string[];  // Node IDs using this variation
  percentage: number;  // Percentage of total pattern instances
  characteristics?: Record<string, any>;
}

interface CASPatternDeviation {
  type: 'inconsistent-adoption' | 'partial-implementation' |
        'anti-pattern' | 'obsolete-usage' | 'mixed-styles';
  severity: 'info' | 'warning' | 'error';
  description: string;
  affected_instances: string[];
  recommendation?: string;
}
```

### 3. Enhanced Entry Point Schema

```typescript
interface EntryPoint {
  // ... existing fields ...

  trigger: {
    method: string;           // GET, POST, etc.
    path: string;             // MUST be full path: /workspaces/:id NOT just :id
    base_path?: string;       // Controller base path
    parameters?: Parameter[];
  };

  security: {
    authenticated: boolean;   // MUST merge class-level and method-level guards
    guards: string[];         // ALL guards (class + method level)
    roles?: string[];
    permissions?: string[];
  };
}
```

**Semantic Rules:**

1. `trigger.path` MUST include controller base path
2. `security.guards` MUST include class-level guards from `@UseGuards()` on controller
3. `security.authenticated` MUST be true if ANY guard is an auth guard (JwtAuthGuard, AuthGuard, etc.)

### 4. Node Parent Requirements

```typescript
interface CASNode {
  // ... existing fields ...

  parent?: string;  // MUST be set for class members (methods, properties, constructors)
}
```

**Semantic Rules:**

1. Methods MUST have `parent` set to containing class node ID
2. Properties MUST have `parent` set to containing class node ID
3. Constructors MUST have `parent` set to containing class node ID
4. Nested classes MUST have `parent` set to containing class node ID

```typescript
interface ExternalService {

interface CASOutput {
  // ... existing fields ...
```

### 6. Anonymous Function Handling

```typescript
interface CASMethodCall {
  // ... existing fields ...

  anonymous_context?: {
    containing_function: string;  // Node ID of containing named function
    callback_position?: number;   // Position in arguments list
    closure_type: 'arrow' | 'function-expression' | 'callback';
  };
}
```

**Semantic Rules:**

1. When anonymous function makes a call, attribute to containing named function
2. Do NOT create orphan nodes for anonymous functions
3. Track closure context for debugging

### 7. Repository Detection Enhancement

Data access layer detection MUST NOT require `@Injectable()` decorator.

**Detection Methods (in order of priority):**

1. **Decorator-based**: `@Injectable()`, `@Repository()`, `@Entity()`
2. **Inheritance-based**: `extends Repository`, `extends BaseRepository`, `extends EntityRepository`
3. **Naming convention**:
   - Class name: `*Repository`, `*Repo`, `*DAO`
   - File path: `/repositories/`, `/repos/`, `/daos/`
4. **Usage pattern**: Uses `Pool`, `EntityManager`, `QueryBuilder`, `DataSource`

### 8. Constructor Stub Detection Improvement

```typescript
interface CASImplementationStatus {
  // ... existing fields ...

  indicators: {
    // ... existing fields ...

    is_di_constructor: boolean;  // true if constructor only has DI params
    is_framework_valid: boolean; // true if framework validates empty body
  };
}
```

**Detection Logic:**

1. Check if constructor has ONLY parameter properties (`private readonly`, `public`, etc.)
2. Check if class has framework decorator (`@Injectable`, `@Controller`, etc.)
3. If both true, constructor is NOT a stub even with empty body

1. Update `cas_version` to "1.5.0"

## Conclusion

CAS v1.5.0 addresses the critical gap between method-level analysis and class-level visualization. By adding proper class relationship edges, pattern variations, and fixing framework-specific detection, the visualization layer can accurately display:

- Which services call which repositories
- Which controllers depend on which services
- Pattern adoption consistency across the codebase
- Correct authentication status for all endpoints

This eliminates the need for frontend computation of relationships and provides a complete, accurate picture of system architecture.
