# Code Analysis Specification v1.1.0

## Abstract

This document extends the Code Analysis Specification (CAS) v1.0.0 to support multi-perspective analysis through a flexible tagging and perspective system, along with comprehensive metadata for runtime correlation, external services, cross-repository linking, and progressive disclosure. This specification defines a universal format for representing code analysis results that can accommodate multiple analytical viewpoints simultaneously.

## 1. Introduction

### 1.1 Motivation

Modern software systems are understood through multiple lenses. A single code element may be:
- A class in the language domain
- A controller in a web framework
- A command handler in a CQRS pattern
- A user management component in the business domain
- Located in a specific folder structure

Version 1.1.0 enables all these perspectives to coexist within a single analysis result while providing rich metadata for documentation, security, metrics, and runtime correlation.

### 1.2 Design Goals

- **Flexibility**: Support any number of analytical perspectives
- **Extensibility**: Allow new perspectives without breaking existing ones
- **Composability**: Enable querying across multiple perspectives
- **Independence**: Each perspective maintains its own organizational structure
- **Completeness**: Capture all aspects needed for comprehensive system understanding

## 2. Specification

### 2.1 Node Structure

A CAS v1.1.0 node is defined as:

```typescript
interface CASNode {
  // Identification
  id: string;
  name: string;

  // Classification through tags
  tags: string[];

  // Multiple analytical perspectives
  perspectives: {
    [perspectiveId: string]: {
      hierarchy: string[];
      level: number;
      priority: number;
      metadata?: Record<string, any>;
    }
  };

  // Contributing analyzers
  analyzers: string[];

  // Primary ownership
  primaryAnalyzer: string;

  // Source location
  source: {
    file: string;
    line: number;
    end_line?: number;
    column?: number;
    end_column?: number;
  };

  // Typed relationships
  relationships: {
    [relationshipType: string]: string[];
  };

  // Rich documentation
  documentation?: {
    description?: string;
    purpose?: string;
    businessContext?: string;
    examples?: string[];
    contracts?: Record<string, any>;
    usage?: string;
  };

  // Quality metrics
  metrics?: {
    complexity?: number;
    coverage?: number;
    testCount?: number;
    issueCount?: number;
    lines?: number;
    maintainability?: number;
  };

  // Security context
  security?: {
    accessLevel?: 'public' | 'protected' | 'private';
    authRequired?: boolean;
    permissions?: string[];
    roles?: string[];
    threats?: string[];
  };

  // Runtime correlation
  telemetry?: {
    correlationId?: string;
    expectedLoad?: number;
    sla?: Record<string, any>;
    baseline?: Record<string, any>;
  };

  // Data handling
  dataFlow?: {
    inputs?: Record<string, any>;
    outputs?: Record<string, any>;
    transformations?: string[];
    validations?: string[];
    sideEffects?: string[];
  };

  // Standard metadata
  metadata?: Record<string, any>;
}
```

### 2.2 Edge Structure

Edges in v1.1.0 include analyzer attribution and data flow information:

```typescript
interface CASEdge {
  id: string;

  // Edge metadata
  metadata?: Record<string, any>;

```


### 2.5 Tag System

Tags are non-hierarchical labels that classify nodes. A node accumulates tags from all analyzers that process it.

Example tags might include:
- Language constructs: `class`, `function`, `variable`
- Framework patterns: `controller`, `component`, `service`
- Architectural patterns: `repository`, `factory`, `observer`
- Domain concepts: `authentication`, `payment`, `user-management`
- Structural markers: `public`, `private`, `abstract`, `async`
- Quality markers: `deprecated`, `todo`, `hack`, `critical`

### 2.6 Perspective System

Each analyzer contributes a perspective containing:

- **hierarchy**: The node's position in this perspective's organization
- **level**: The depth within this perspective (0 = top-level)
- **priority**: The importance of this node in this perspective
- **metadata**: Perspective-specific information

## 3. Semantic Definitions

### 3.1 Perspectives

A **perspective** is a particular way of organizing and understanding a codebase. Examples include:

- **Language perspectives**: Organization by language constructs
- **Framework perspectives**: Organization by framework patterns
- **Architectural perspectives**: Organization by architectural layers
- **Domain perspectives**: Organization by business domains
- **Structural perspectives**: Organization by file/folder structure
- **Quality perspectives**: Organization by metrics and issues
- **Security perspectives**: Organization by security boundaries

### 3.2 Analyzer Collaboration

Multiple analyzers may process the same node:

1. Initial analyzer creates the node
2. Subsequent analyzers add:
   - Additional tags
   - Their perspective
   - Additional relationships
   - Enhanced metadata
   - Documentation
   - Metrics
   - Security information

### 3.3 Primary Analyzer

The `primaryAnalyzer` field indicates which analyzer has the strongest claim to a node, typically the most specific analyzer that can classify it.

### 3.4 External Service Classification

External services are classified by:
- **Type**: The kind of service (database, API, cache, etc.)
- **Direction**: Whether data flows to it (production), from it (consumption), or both
- **Connection**: Which node in the system connects to it

### 3.5 Progressive Disclosure

Progressive disclosure enables:
- Starting with high-level overview
- Drilling into specific areas
- Maintaining context while exploring
- Efficient information transfer

## 4. Query Semantics

### 4.1 Tag-Based Queries

Nodes can be queried by tags using set operations:

- **Union**: Nodes with any of the specified tags
- **Intersection**: Nodes with all specified tags
- **Exclusion**: Nodes without specified tags

### 4.2 Perspective-Based Queries

Nodes can be queried within specific perspectives:

- By perspective presence
- By level within a perspective
- By hierarchy path within a perspective

### 4.3 Composite Queries

Queries can combine multiple perspectives:

```
Find all nodes that:
- Have perspective "dotnet"
- Have perspective "webapi"
- Have perspective "mediatr"
- Are tagged with "handler"
```

### 4.4 Relationship Traversal

Queries can follow relationships:

- Direct relationships
- Transitive relationships
- Relationship type filtering
- Bidirectional traversal

## 5. Compatibility

### 5.1 Relationship with v1.0.0

CAS v1.1.0 is a superset of v1.0.0. Migration involves:

- `type` → primary tag
- `subcategories` → additional tags
- `level` → perspective-specific levels
- Single hierarchy → multiple perspective hierarchies
- Simple metadata → structured metadata with specific fields

### 5.2 Analyzer Requirements

Analyzers conforming to CAS v1.1.0 must:

1. Define their perspective identifier
2. Document their tag vocabulary
3. Specify their hierarchical organization
4. Declare their enhancement strategy
5. Identify external services when detected
6. Extract documentation when available
7. Calculate metrics when applicable

## 7. Extensibility

The specification is designed to accommodate:

- New types of analyzers
- New perspective organizations
- New tag vocabularies
- New relationship types
- New external service types
- New metadata fields

Without breaking existing consumers or requiring specification changes.

## 8. Conformance

An implementation conforms to CAS v1.1.0 if it:

1. Produces output matching the specified structure
2. Correctly implements tag accumulation
3. Maintains perspective independence
4. Preserves analyzer attribution
5. Properly classifies external services
6. Supports progressive disclosure hints

## Appendices

### A. Changes from v1.0.0

- Replaced single type system with tag-based classification
- Introduced multi-perspective organization
- Added analyzer attribution and collaboration
- Enhanced relationship typing
- Added external service tracking
- Added cross-repository linking
- Added dependency information
- Added rich documentation structure
- Added security context
- Added quality metrics
- Added runtime correlation support
- Added data flow tracking
- Added progressive disclosure support

### B. Reserved Fields

The following field names are reserved for future specification versions:
- `version` (on nodes)
- `schema` (on perspectives)
- `constraints` (on relationships)
- `policies` (on security)
- `workflows` (on dataFlow)

### C. Implementation Notes

Implementations are free to:
- Define their own perspective identifiers
- Create analyzer-specific tags
- Implement additional metadata fields
- Optimize storage and query mechanisms
- Add implementation-specific fields prefixed with underscore

As long as the output conforms to this specification.
