# CAS v1.7.1 Frontend Addendum

**Version:** 1.7.1
**Status:** Draft
**Created:** 2026-02-04
**Extends:** v1.7.0

## Executive Summary

This addendum extends CAS v1.7.0 to address frontend-specific analysis concerns. Frontend applications operate in fundamentally different environments than backend systems: state lives in the browser, navigation replaces HTTP routing, data is cached ephemerally, and component reuse is a primary architectural concern. This addendum formalizes the structures needed to fully analyze single-page applications, component-based frameworks, client-side state management, and data fetching patterns.

## Problem Statement

### Current Limitations (v1.7.0)

1. **No Client-Side Data Model**: `CASDataEntity` assumes server-side persistence (ORM models, database schemas). Frontend state (Redux stores, Zustand stores, Pinia stores, component state) has no representation.

2. **Limited Exit Point Vocabulary**: Exit point types (`database`, `api`, `file`, `message`, `cache`, `sdk`, `webhook`) cover backend interactions but miss client-side operations: route navigation, localStorage writes, analytics dispatches.

3. **No Component Reuse Analysis**: Components are the primary unit of frontend architecture, but CAS has no metrics for component usage, prop surface area, or slot complexity.

4. **No Navigation Flow Model**: Backend routing maps cleanly to entry points, but frontend routing creates an internal navigation graph with guards, lazy loading, and nested layouts that has no CAS representation.

5. **No State Management Model**: Client-side state stores (Redux, Zustand, Pinia, Vuex) are a core architectural layer with their own topology of actions, selectors, subscriptions, and middleware. CAS has no formalized model for this.

6. **No Data Fetching Model**: Libraries like TanStack Query, SWR, and RTK Query create a caching and synchronization layer between client and server that is invisible to current CAS analysis.

7. **Incomplete Change Risk for Frontend**: `CASChangeRisk` factors (`many-callers`, `critical-path`, etc.) don't account for shared component blast radius, state shape changes, or route graph impact.

### Root Cause

CAS was designed primarily for backend systems where entry points are HTTP endpoints, data lives in databases, and the execution model is request-response. Frontend applications have a different execution model: event-driven, component-based, with client-side state as the primary data layer.

## 1. Client-Side Data Entities

**Purpose:** Represent client-side state as first-class data entities in CAS analysis.

**Extends:** `CASDataEntity` (v1.7.0)

### Data Structures

```typescript
interface CASClientDataEntity extends CASDataEntity {
  storage_type: 'component_state' | 'store' | 'local_storage' | 'session_storage' |
                'indexed_db' | 'url_params' | 'cookie' | 'cache';

  persistence: 'ephemeral' | 'session' | 'persistent';

  scope: 'component' | 'store' | 'global' | 'route';

  sync_source?: {
    type: 'api' | 'websocket' | 'sse' | 'polling';
    endpoint?: string;
    refresh_strategy?: 'on_mount' | 'on_focus' | 'interval' | 'manual' | 'realtime';
  };

  subscribers?: string[];
}
```

### Storage Type Classification

| Storage Type | Detection Source | Persistence | Scope |
|-------------|-----------------|-------------|-------|
| `component_state` | `useState`, `useReducer`, Options API `data()` | ephemeral | component |
| `store` | Redux `createSlice`, Zustand `create`, Pinia `defineStore`, Vuex store | ephemeral or session | store |
| `local_storage` | `localStorage.setItem`, persist middleware | persistent | global |
| `session_storage` | `sessionStorage.setItem` | session | global |
| `indexed_db` | IndexedDB API calls | persistent | global |
| `url_params` | `useSearchParams`, query string manipulation | session | route |
| `cookie` | `document.cookie`, cookie libraries | persistent or session | global |
| `cache` | TanStack Query cache, SWR cache, RTK Query cache | ephemeral | global |

### Sensitive Field Detection (Frontend Extension)

In addition to v1.7.0 rules, fields SHOULD be marked `is_sensitive: true` when:
- State key contains `auth`, `user`, `session`, `jwt`
- State is synced from an authenticated API endpoint
- State contains values extracted from cookies or auth headers

### Semantic Rules

**Rule 5.24 - Client Data Entities:**
- Client-side state MUST be represented as `CASClientDataEntity` with appropriate `storage_type`
- `persistence` MUST reflect actual data lifetime: `'ephemeral'` for in-memory only, `'session'` for tab lifetime, `'persistent'` for cross-session
- `scope` MUST reflect the access pattern: `'component'` for local state, `'store'` for state management, `'global'` for window-level, `'route'` for URL-bound
- `subscribers` SHOULD list node IDs of components that consume this state
- `sync_source` SHOULD be populated when state is derived from an external data source
- `lifecycle.created_by` MUST reference the node that initializes the state (store definition, component mount, etc.)

### Example

```json
{
  "data_entities": [
    {
      "id": "entity_client_auth_state",
      "name": "AuthState",
      "storage_type": "store",
      "persistence": "session",
      "scope": "store",
      "fields": [
        { "name": "user", "type": "User | null", "is_sensitive": true },
        { "name": "token", "type": "string | null", "is_sensitive": true },
        { "name": "isAuthenticated", "type": "boolean", "is_sensitive": false }
      ],
      "lifecycle": {
        "created_by": ["function_create_auth_store"],
        "read_by": ["component_navbar", "component_profile", "guard_auth_route"],
        "updated_by": ["function_login_action", "function_logout_action"],
        "deleted_by": ["function_logout_action"]
      },
      "sync_source": {
        "type": "api",
        "endpoint": "/api/auth/me",
        "refresh_strategy": "on_mount"
      },
      "subscribers": ["component_navbar", "component_profile", "component_sidebar"]
    }
  ]
}
```

## 2. Frontend Entry Point Types

**Purpose:** Formalize frontend-specific entry point semantics within the existing type union.

**Extends:** `CASEntryPoint.type` (v1.1.0)

### Additions to Entry Point Vocabulary

The existing `CASEntryPoint.type` union already includes `'route'`, `'event'`, and `'page'`. This addendum formalizes their usage for frontend analysis and adds `'lifecycle'`.

```typescript
interface CASEntryPoint {
  // Existing type union extended:
  type: 'http' | 'websocket' | 'cli' | 'event' | 'schedule' | 'page' | 'route' |
        'message' | 'file' | 'test' | 'lifecycle';
  // ... existing fields ...
}
```

### Frontend Entry Point Semantics

| Type | Frontend Usage | Detection |
|------|---------------|-----------|
| `route` | Each navigable client-side route | React Router `<Route>`, Angular `RouterModule.forRoot`, Vue Router `createRouter` |
| `page` | Framework-generated pages | Next.js `app/` and `pages/`, Nuxt pages, Angular route components |
| `event` | DOM events, custom events, message events | `addEventListener`, framework event bindings, `window.postMessage` handlers |
| `lifecycle` | Component mount/unmount, route guard activation | `useEffect` on mount, `ngOnInit`, `mounted()`, route `beforeEnter` |

### Semantic Rules

**Rule 5.25 - Frontend Entry Points:**
- Each navigable route MUST produce an entry point with `type: 'route'`
- Route entry points MUST include `trigger.path` with the route pattern
- Route entry points SHOULD include `trigger.parameters` for dynamic segments
- `type: 'lifecycle'` SHOULD be used for component initialization that triggers significant side effects (data fetching, subscriptions)
- Framework-specific pages (Next.js, Nuxt, etc.) SHOULD use `type: 'page'`
- Route guards SHOULD produce `type: 'lifecycle'` entry points with `security` metadata populated

### Example

```json
{
  "entry_points": [
    {
      "id": "entry_route_dashboard",
      "source_node": "component_dashboard_page",
      "type": "route",
      "name": "GET /dashboard",
      "trigger": {
        "path": "/dashboard",
        "method": "GET"
      },
      "security": {
        "authentication": { "required": true, "mechanism": "route_guard" },
        "guards": ["guard_auth_required"]
      },
      "metadata": {
        "framework": "react-router",
        "lazy": true,
        "layout": "authenticated_layout"
      }
    }
  ]
}
```

## 3. Frontend Exit Point Types

**Purpose:** Represent client-side outbound operations that are invisible to backend-only exit point types.

**Extends:** `CASExitPoint.type` (v1.1.0)

### Additions to Exit Point Type Union

```typescript
interface CASExitPoint {
  // Existing type union extended:
  type: 'database' | 'api' | 'file' | 'message' | 'cache' | 'sdk' | 'webhook' |
        'navigation' | 'client_storage' | 'analytics';
  // ... existing fields ...
}
```

### Frontend Exit Point Semantics

| Type | Purpose | Detection |
|------|---------|-----------|
| `navigation` | Client-side route transitions | `useNavigate()`, `router.push()`, `Link` click handlers, `window.location` |
| `client_storage` | Browser storage writes | `localStorage.setItem`, `sessionStorage.setItem`, IndexedDB transactions, `document.cookie` writes |
| `analytics` | Tracking and analytics event dispatches | `gtag()`, `analytics.track()`, `posthog.capture()`, `mixpanel.track()` |

### Semantic Rules

**Rule 5.26 - Frontend Exit Points:**
- Navigation calls MUST produce exit points with `type: 'navigation'` and `target.endpoint` set to the destination route
- Client storage writes MUST produce exit points with `type: 'client_storage'` and `target.resource` set to the storage key
- Analytics dispatches SHOULD produce exit points with `type: 'analytics'` and `target.service_id` set to the analytics provider
- `type: 'sdk'` SHOULD be used for third-party SDK invocations (Stripe, Auth0, Firebase) that are not purely analytics
- Existing `type: 'api'` remains the correct type for HTTP/fetch calls from the frontend

### Example

```json
{
  "exit_points": [
    {
      "id": "exit_navigate_profile",
      "source_node": "component_user_menu",
      "type": "navigation",
      "name": "Navigate to /profile",
      "target": {
        "endpoint": "/profile"
      },
      "metadata": {
        "framework": "react-router",
        "method": "useNavigate"
      }
    },
    {
      "id": "exit_persist_theme",
      "source_node": "function_toggle_theme",
      "type": "client_storage",
      "name": "Persist theme preference",
      "target": {
        "service_id": "localStorage",
        "resource": "theme"
      }
    }
  ]
}
```

## 4. Component Reuse Metrics

**Purpose:** Quantify component reuse patterns to inform change risk and architecture quality.

### Data Structures

```typescript
interface CASComponentMetrics {
  node_id: string;

  usage_count: number;
  usage_locations: string[];

  prop_surface: {
    total: number;
    required: number;
    optional: number;
    with_defaults: number;
  };

  slot_count: number;
  slot_names?: string[];

  shared_across_routes: boolean;
  route_count?: number;

  composition: {
    child_components: string[];
    parent_components: string[];
    depth_in_tree: number;
  };
}

interface CASComponentMetricsSummary {
  most_reused: Array<{ node_id: string; usage_count: number }>;
  largest_prop_surface: Array<{ node_id: string; prop_count: number }>;
  orphaned_components: string[];
  deeply_nested: Array<{ node_id: string; depth: number }>;
}
```

### Reuse Detection

| Metric | Detection Method |
|--------|-----------------|
| `usage_count` | Count import statements + JSX/template references across files |
| `prop_surface` | Count interface/type properties for component props |
| `slot_count` | Count `<slot>` elements, `children` props, `ng-content`, content projection |
| `shared_across_routes` | Track which route components transitively render this component |

### Semantic Rules

**Rule 5.27 - Component Metrics:**
- Components with `usage_count >= 5` SHOULD be flagged as widely shared
- `prop_surface.total` SHOULD count all props including inherited
- `shared_across_routes` MUST be true when the component appears in 2+ route subtrees
- `orphaned_components` MUST list components with `usage_count == 0` (defined but never imported)
- Component metrics MUST be attached as metadata on the component's `CASNode`

## 5. Navigation Flow Model

**Purpose:** Represent the client-side route graph as a first-class CAS concept.

### Data Structures

```typescript
interface CASNavigationFlow {
  routes: CASRouteNode[];
  navigation_edges: CASNavigationEdge[];
  guards: CASRouteGuard[];
  layouts: CASLayoutNode[];
}

interface CASRouteNode {
  id: string;
  path: string;
  name?: string;
  component_node_id: string;
  parent_route_id?: string;

  lazy: boolean;
  index: boolean;

  params: Array<{
    name: string;
    type: 'path' | 'query' | 'hash';
    required: boolean;
  }>;

  guards: string[];
  layout_id?: string;
  metadata?: Record<string, any>;
}

interface CASNavigationEdge {
  id: string;
  source_route_id: string;
  target_route_id: string;
  type: 'redirect' | 'programmatic' | 'link' | 'fallback';
  source_node_id?: string;
  condition?: string;
}

interface CASRouteGuard {
  id: string;
  name: string;
  type: 'authentication' | 'authorization' | 'feature_flag' | 'data_resolver' | 'confirmation';
  node_id: string;
  protected_routes: string[];
  redirect_on_fail?: string;
}

interface CASLayoutNode {
  id: string;
  name: string;
  component_node_id: string;
  child_routes: string[];
}
```

### Route Detection

| Framework | Route Config Source |
|-----------|-------------------|
| React Router v5 | `<Route path="..." component={...}>` in JSX |
| React Router v6 | `createBrowserRouter`, `<Route path="..." element={...}>`, route objects |
| Angular | `RouterModule.forRoot(routes)`, `provideRouter(routes)`, route config arrays |
| Vue Router | `createRouter({ routes })`, route config arrays |
| Next.js | File system: `app/` directory structure, `pages/` directory structure |
| Nuxt | File system: `pages/` directory structure |

### Semantic Rules

**Rule 5.28 - Navigation Flow:**
- Each route definition MUST produce a `CASRouteNode`
- Nested routes MUST reference `parent_route_id`
- Lazy-loaded routes MUST have `lazy: true` and SHOULD be annotated as code splitting boundaries
- Route guards MUST produce `CASRouteGuard` entries and map to `CASSecurityBoundary` when they enforce authentication or authorization
- Programmatic navigation calls MUST produce `CASNavigationEdge` entries with `type: 'programmatic'`
- `<Link>` / `<router-link>` / `routerLink` usages SHOULD produce `CASNavigationEdge` entries with `type: 'link'`
- Redirect routes MUST produce `CASNavigationEdge` entries with `type: 'redirect'`

### Example

```json
{
  "navigation_flow": {
    "routes": [
      {
        "id": "route_dashboard",
        "path": "/dashboard",
        "component_node_id": "component_dashboard",
        "lazy": true,
        "index": false,
        "params": [],
        "guards": ["guard_auth"],
        "layout_id": "layout_authenticated"
      },
      {
        "id": "route_user_profile",
        "path": "/users/:id",
        "component_node_id": "component_user_profile",
        "lazy": false,
        "index": false,
        "params": [{ "name": "id", "type": "path", "required": true }],
        "guards": ["guard_auth"],
        "layout_id": "layout_authenticated"
      }
    ],
    "navigation_edges": [
      {
        "id": "nav_login_to_dashboard",
        "source_route_id": "route_login",
        "target_route_id": "route_dashboard",
        "type": "programmatic",
        "source_node_id": "function_handle_login_success"
      }
    ],
    "guards": [
      {
        "id": "guard_auth",
        "name": "AuthGuard",
        "type": "authentication",
        "node_id": "function_require_auth",
        "protected_routes": ["route_dashboard", "route_user_profile"],
        "redirect_on_fail": "/login"
      }
    ]
  }
}
```

```typescript
  store_id: string;
  subscriber_node_id: string;

}

  id: string;

  action_name: string;
  dispatcher_node_id: string;
  conditional: boolean;
}

  id: string;
  name: string;
  store_id: string;
  node_id: string;
  input_selectors: string[];
  memoized: boolean;
}
```

### Store Detection

| Framework | Detection Pattern |
|-----------|------------------|
| Redux/RTK | `configureStore`, `createSlice`, `createStore` |
| Zustand | `create()` from zustand imports |
| Pinia | `defineStore` |
| Vuex | `createStore` from vuex, `new Vuex.Store` |
| MobX | `makeObservable`, `makeAutoObservable` |
| NgRx | `createReducer`, `createAction`, `createEffect` |
| React Context | `createContext` + `useContext` as state provider |

### Semantic Rules

**Rule 5.29 - State Management:**
- Each state store definition MUST produce a `CASStateStore`
- Store `state_shape` MUST list top-level state keys with types
- Actions that trigger API calls MUST have `triggers_api_call: true` and produce corresponding exit points
- Subscriptions MUST link store to consuming component nodes
- Selectors with `memoized: true` SHOULD be annotated with their input selector dependencies
- `persistence` MUST be populated when persist middleware is detected
- Cross-store dependencies SHOULD be represented as edges between `CASStateStore` nodes

### Example

```json
          { "name": "persist", "type": "persistence" },

        ],
        "persistence": {
          "storage_type": "local_storage",
          "keys": ["items"]
        }
      }
    ],
    "subscriptions": [
      {
        "id": "sub_cart_header",
        "store_id": "store_cart",
```

## 7. Data Fetching Model

**Purpose:** Represent client-server data synchronization patterns as a CAS concept.

### Data Structures

```typescript
interface CASDataFetching {
  queries: CASQuery[];
  mutations: CASMutation[];
  invalidation_rules: CASInvalidationRule[];
}

interface CASQuery {
  id: string;
  name: string;
  framework: 'tanstack_query' | 'swr' | 'rtk_query' | 'apollo' | 'urql' | 'custom';
  node_id: string;

  key: string | string[];
  endpoint?: string;

  config: {
    stale_time?: string;
    cache_time?: string;
    retry?: number | boolean;
    refetch_on_window_focus?: boolean;
    refetch_interval?: string;
    suspense?: boolean;
    enabled_condition?: string;
  };

  consumers: string[];
  error_boundary?: string;
  loading_boundary?: string;
}

interface CASMutation {
  id: string;
  name: string;
  framework: string;
  node_id: string;

  endpoint?: string;
  method?: string;
  invalidates: string[];
  optimistic_update?: boolean;

  on_success_actions?: string[];
  on_error_actions?: string[];
}

interface CASInvalidationRule {
  mutation_id: string;
  invalidated_query_ids: string[];
  strategy: 'refetch' | 'remove' | 'update' | 'optimistic';
}
```

### Detection Patterns

| Framework | Query Detection | Mutation Detection |
|-----------|----------------|-------------------|
| TanStack Query | `useQuery`, `useSuspenseQuery`, `useInfiniteQuery` | `useMutation` |
| SWR | `useSWR`, `useSWRInfinite` | `useSWRMutation` |
| RTK Query | `useXxxQuery` from generated hooks | `useXxxMutation` from generated hooks |
| Apollo | `useQuery`, `useLazyQuery` | `useMutation` |

### Semantic Rules

**Rule 5.30 - Data Fetching:**
- Each query hook call MUST produce a `CASQuery`
- Each mutation hook call MUST produce a `CASMutation`
- `CASQuery.endpoint` SHOULD be extracted from the query function when it contains a URL or API path
- Queries MUST produce exit points with `type: 'api'` and `target.endpoint` matching the API URL
- Mutation invalidation patterns MUST be captured as `CASInvalidationRule`
- `CASQuery.consumers` MUST list component node IDs that use this query
- Cache entries SHOULD be represented as `CASClientDataEntity` with `storage_type: 'cache'` and `persistence: 'ephemeral'`

### Example

```json
{

    "queries": [
      {

        "key": ["users"],
        "endpoint": "/api/users",
        "config": {
          "stale_time": "5m",
          "refetch_on_window_focus": true
        },
        "consumers": ["component_user_table", "component_user_search"]
      }
    ],
    "mutations": [
      {
        "id": "mutation_create_user",
        "name": "useCreateUser",
        "framework": "tanstack_query",
        "node_id": "function_use_create_user",
        "endpoint": "/api/users",
        "method": "POST",
        "invalidates": ["query_user_list"],
        "optimistic_update": false
      }
    ],
    "invalidation_rules": [
      {
        "mutation_id": "mutation_create_user",
        "invalidated_query_ids": ["query_user_list"],
        "strategy": "refetch"
      }
    ]
  }
}
```

## 8. Frontend-Specific Change Risk Factors

**Purpose:** Extend `CASChangeRisk` with factors specific to frontend architecture.

**Extends:** `ChangeRiskFactor.factor` (v1.7.0)

### Additional Risk Factors

```typescript
interface ChangeRiskFactor {
  factor: 'many-callers' | 'critical-path' | 'high-traffic' |
          'no-tests' | 'recent-bugs' | 'complex-logic' |
          'external-dependency' | 'security-sensitive' |
          // v1.7.1 additions:
          'shared-component' | 'state-shape-change' |
          'route-graph-impact' | 'cross-store-dependency';
  severity: 'high' | 'medium' | 'low';
  details: string;
}
```

### Frontend Risk Calculation

| Factor | Severity | Condition |
|--------|----------|-----------|
| `shared-component` | high | Component `usage_count >= 10` |
| `shared-component` | medium | Component `usage_count >= 5` AND `shared_across_routes: true` |
| `state-shape-change` | high | Store state shape modification when `subscribers.length >= 5` |
| `route-graph-impact` | medium | Route change affects navigation edges or guard configuration |
| `cross-store-dependency` | medium | Store action dispatches to or reads from another store |

### Semantic Rules

**Rule 5.31 - Frontend Change Risk:**
- Components with `usage_count >= 10` MUST include `factor: 'shared-component'` with `severity: 'high'`
- State stores with 5+ subscribers MUST include `factor: 'state-shape-change'` with `severity: 'high'` when state shape fields are at risk
- Route changes SHOULD include `factor: 'route-graph-impact'` when they affect navigation edges, guards, or layout assignments
- Cross-store dependencies SHOULD include `factor: 'cross-store-dependency'`
- Frontend change risk factors MUST be combined with existing v1.7.0 risk factors, not replace them

## Conclusion

CAS v1.7.1 extends the specification to fully support frontend application analysis. The key additions are:

1. **Client-side data entities** with storage type, persistence, and scope classification
2. **Extended entry/exit point types** for navigation, client storage, and analytics
3. **Component reuse metrics** for change risk and architecture quality assessment
4. **Navigation flow model** with routes, guards, edges, and layouts
5. **State management model** with stores, subscriptions, dispatches, and selectors
6. **Data fetching model** with queries, mutations, and cache invalidation rules
7. **Frontend-specific change risk factors** for shared components, state shapes, and route graphs

This enables answering frontend-specific questions:
- "Which components will break if I change this prop interface?" (Component Metrics + Change Risk)
- "What happens to the state when the user logs out?" (State Management + Data Entities)
- "Which API calls will re-execute if this mutation succeeds?" (Data Fetching + Invalidation)
- "Is this route protected?" (Navigation Flow + Guards + Security Boundaries)
- "Where does this user data live on the client?" (Client Data Entities)
- "What is the navigation structure of this app?" (Navigation Flow)
