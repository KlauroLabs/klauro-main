# CAS v1.10.0 RFP: Graph-Anchored Semantic Retrieval

**Version:** 1.10.0
**Status:** Draft, revised after independent review
**Author:** Klauro Team
**Date:** 2026-05-19

## Review Status

This RFP was revised after an independent architecture review. The review found two
correctness blockers that are now resolved in the specification:

1. Incremental re-embedding driven only by `changeReport` would miss nodes whose
   embedding document changed because an enriched neighbor changed. Re-embedding is
   now driven by a full document-hash reconciliation; `changeReport` is a fast-path
   hint only, never a correctness boundary.
2. Full rebuilds and node-ID churn (renames, moves) would orphan vectors. Every
   embedding run, full or incremental, now reconciles the stored ID set against the
   live node-ID set and deletes the difference.

Further review-driven changes: source text is captured at analysis time and never
re-read at embed time; `body_hash` is folded into the document hash; the embedding
phase runs under a wall-clock budget; int8 quantization is in scope rather than
deferred; vector-store writes are atomic; the pgvector index is tenant-scoped.

## Abstract

This RFP adds a semantic retrieval layer to CAS. Every CAS node gains a vector embedding derived from a structured, graph-aware document. A new hybrid query path fuses lexical matching, vector similarity, and structural re-ranking so that natural-language questions resolve to graph-anchored nodes, not context-free text chunks.

The embedding layer is built into CAS as a first-class concern: the analyzer produces it, incremental analysis keeps it fresh, the MCP surface queries it, and CAS records its provenance. Embedding vectors are stored out-of-band so the CAS schema change stays additive and optional.

## Motivation

CAS already gives agents structural truth: callers, callees, flows, risk, tests, idioms. The remaining gap is the entry point into that structure. Today `searchNodes()` is a linear lexical scan over `name`, `qualified_name`, and `description`. A question like "where do we handle refund webhooks" fails when no node carries the word "refund".

Embedding-based retrieval tools answer that fuzzy question but return disconnected chunks: the consumer still has to rediscover how a chunk connects to anything.

Klauro can do both at once. A semantic hit should return a node that already carries its callers, callees, tests, risk, and framework role. Retrieval becomes the doorway into the graph rather than a parallel system beside it.

### Goals

1. **Semantic node retrieval**: natural-language queries resolve to the right CAS nodes even without lexical overlap.
2. **Graph-anchored results**: every semantic hit returns a node with its structural context attached.
3. **Structural re-ranking**: ranking blends semantic similarity with graph signals, not cosine alone.
4. **Always-fresh index**: incremental analysis re-embeds only changed nodes; the index never lags the graph.
5. **Provenance**: CAS records which model, dimensions, and document version produced the index.
6. **Deployment parity**: works in local CLI mode (file-backed) and hosted mode (pgvector-backed).
7. **Better target inference**: agent work-packet resolution uses semantic retrieval to locate targets for no-target tasks.

### Non-Goals

1. Embedding files that produce no CAS nodes (universal non-framework text coverage) — deferred to v1.11.0.
2. Approximate-nearest-neighbor indexing for very large repos beyond the pgvector HNSW path — deferred; brute-force file store plus pgvector HNSW is sufficient at current scale.
3. Cross-encoder re-ranking — deferred to v1.11.0.
4. A frontend semantic-search surface — MCP first; UI is a later addendum.
5. Replacing lexical search — lexical remains and is fused, not removed.

## Specification

### 4.13 Semantic Retrieval Structures (v1.10.0)

#### CASEmbeddingIndex

Recorded on `CASOutput` as the optional top-level field `embedding_index`. Metadata only. It MUST NOT contain vectors.

```typescript
interface CASEmbeddingIndex {
  model: string;                       // e.g. "voyage-code-3"
  provider: string;                    // "api" | "local"
  dimensions: number;                  // vector dimensionality
  document_version: string;            // version of embedding-document composition logic
  store: 'file' | 'pgvector';          // where vectors live
  generated_at: string;                // ISO 8601
  node_count: number;                  // nodes considered
  coverage: {
    embedded: number;                  // nodes with a current embedding
    skipped: number;                   // nodes intentionally not embedded
    failed: number;                    // nodes whose embedding errored
  };
  degraded?: boolean;                  // true if the index is incomplete or stale
  degraded_reason?: string;            // human-readable explanation when degraded
}
```

#### NodeEmbeddingRecord

The unit stored in the vector store. Never serialized into CAS.

```typescript
interface NodeEmbeddingRecord {
  node_id: string;                     // CAS node ID
  analysis_id: string;                 // owning analysis
  vector: Float32Array;                // length === CASEmbeddingIndex.dimensions
  embedding_doc_hash: string;          // SHA256 (16 char) of the composed document
  model: string;                       // model that produced this vector
  document_version: string;            // composition logic version
  created_at: string;                  // ISO 8601
}
```

#### EmbeddingDocument

The structured text that gets embedded for a node. It is composed deterministically; it is the "graph-anchored" part of the design.

```typescript
interface EmbeddingDocument {
  node_id: string;
  text: string;                        // the document fed to the embedding model
  doc_hash: string;                    // SHA256 (16 char) of `text`
}
```

The composed `text` MUST include, in this order, any parts that are present:

1. Framework role and node type, e.g. `NestJS controller` or `React hook`.
2. `name` and `qualified_name`.
3. Containing scope: parent class or module name (one hop).
4. `signature` rendered as parameters and return type.
5. `tags`.
6. `documentation.raw` (docstring).
7. Attached `comments` text.
8. Source snippet text captured at analysis time (see below), truncated to `maxDocumentChars` (default 8000).
9. For entry points, the route, method, and guards. For exit points, the target system.

The source snippet MUST come from text captured during analysis, not re-read from
disk at embed time. Re-reading at embed time introduces an uncoordinated staleness
axis: a node not re-analyzed since a file edit would be embedded against a different
code state than the node describes. v1.10.0 therefore requires analyzers to populate
a bounded `source.raw` snippet (capped at `maxDocumentChars`) for every node, or to
carry the snippet in the `FileAnalysisResult` cache so `EmbeddingPhase` reads it from
the in-memory analysis result. The composed `doc_hash` MUST incorporate the node's
`implementation.body_hash` so a body change forces re-embedding even when surface
metadata is unchanged.

#### EmbeddingProvider

Pluggable interface for producing vectors.

```typescript
interface EmbeddingProvider {
  readonly id: string;                 // "api" | "local"
  readonly model: string;
  readonly dimensions: number;
  readonly maxBatch: number;           // max texts per embed call
  embed(texts: string[]): Promise<Float32Array[]>;
}
```

Two implementations:

- `ApiEmbeddingProvider`: default for hosted analysis. Uses a code-specialized embedding model. The analyzer already runs server-side, so source text never leaves a trust boundary the customer has not already crossed for analysis.
- `LocalEmbeddingProvider`: for local CLI mode and self-hosted analyzers that must not call an external embedding API. Uses a deterministic local feature-hash embedding (`klauro-local-hash-v1`) so agent loops have predictable latency with no model download. Lower quality is acceptable; the structural re-rank compensates.

#### VectorStore

Pluggable interface for persisting and querying vectors.

```typescript
interface VectorStore {
  readonly kind: 'file' | 'pgvector';
  upsert(records: NodeEmbeddingRecord[]): Promise<void>;
  deleteNodes(analysisId: string, nodeIds: string[]): Promise<void>;
  deleteAnalysis(analysisId: string): Promise<void>;
  query(
    analysisId: string,
    vector: Float32Array,
    topK: number,
    filter?: { types?: string[]; files?: string[] },
  ): Promise<Array<{ node_id: string; score: number }>>;
  stats(analysisId: string): Promise<{ count: number; model: string; dimensions: number }>;
}
```

Two implementations:

- `FileVectorStore`: local mode. Stores an int8-quantized matrix at `<slug>/embeddings/index.bin` plus `<slug>/embeddings/manifest.json`. Brute-force cosine in memory. int8 quantization (per-vector scale, dequantize on compare) is in scope for v1.10.0: it cuts memory roughly fourfold versus `Float32` and keeps brute-force fast on monorepos that routinely exceed 50k nodes. The manifest stores node-id to row, `embedding_doc_hash` per node, model, dimensions, document version, and for consistency validation: `cas_version`, `analysis_id`, and a CAS content hash. Both files MUST be written atomically via temp-file rename, consistent with `writeJsonAtomic` in `storage.ts`. The keying directory is the project slug, the same key `storage.ts` uses; `analysis_id` is recorded inside the manifest for validation, not used as the path.
- `PgVectorStore`: hosted mode. A `node_embeddings` table in Postgres using the `vector` extension, with a tenant-scoped HNSW index. Added via migration.

#### SemanticSearchResult

Returned by the hybrid query path. Graph-anchored by construction.

```typescript
interface SemanticSearchResult {
  node_id: string;
  name: string;
  qualified_name?: string;
  type: string;
  framework_role?: string;
  file?: string;
  scores: {
    semantic: number;                  // cosine similarity, 0-1
    lexical: number;                   // lexical match score, 0-1
    structural: number;                // graph-signal score, 0-1
    final: number;                     // fused and re-ranked score
  };
  graph_context: {
    caller_count: number;
    callee_count: number;
    test_count: number;
    is_entry_point: boolean;
    risk?: string;
  };
}
```

### Storage Schema (pgvector mode)

Added via MikroORM migration. The `vector` extension MUST be enabled in the same migration.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE node_embeddings (
  id               BIGSERIAL,
  analysis_id      TEXT NOT NULL,
  node_id          TEXT NOT NULL,
  embedding        vector(1024) NOT NULL,
  embedding_doc_hash TEXT NOT NULL,
  model            TEXT NOT NULL,
  document_version TEXT NOT NULL,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (analysis_id, node_id)
) PARTITION BY HASH (analysis_id);
```

The table is partitioned by `analysis_id` so each tenant's vectors live in their own
partition with their own HNSW index. A single global HNSW index with a post-hoc
`analysis_id` filter degrades recall, because the index returns the global top-K
before the tenant filter runs. Each partition gets:

```sql
CREATE INDEX ON node_embeddings_p<n>
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
```

Queries set `hnsw.ef_search` (default 100) per session. The `vector(1024)`
dimensionality MUST match the configured model. On boot, `PgVectorStore` MUST
validate `config.embedding.dimensions` against the live column dimension and refuse
to start on mismatch. If the model changes, a migration MUST be issued; mixed-dimension
rows are not permitted in one table.

### Configuration

Added to `.klaurorc`:

```json
{
  "embedding": {
    "enabled": true,
    "provider": "api",
    "model": "voyage-code-3",
    "apiKeyEnv": "KLAURO_EMBEDDING_API_KEY",
    "dimensions": 1024,
    "maxDocumentChars": 8000,
    "store": "auto"
  }
}
```

`store: "auto"` selects `file` for local analyzer mode and `pgvector` for remote/hosted mode. `enabled: false` skips the embedding phase entirely; CAS still emits, with no `embedding_index`.

### Pipeline Integration

The analyzer gains an `EmbeddingPhase` that runs after all post-processing analyzers
complete — after node enrichment, intent inference, risk, and idiom detection — so the
composed document can include enriched metadata. It is the last analyzer-side phase
before `CASOutput` assembly.

`EmbeddingPhase` performs a full reconciliation against the live graph. It MUST:

1. Compose an `EmbeddingDocument` and `doc_hash` for **every** eligible node in the
   final `CASOutput`. Document composition and hashing are local and cheap; they do
   not call the embedding provider.
2. Load the `VectorStore` manifest for this analysis.
3. Compute three sets:
   - **stale**: nodes whose `doc_hash` differs from the stored hash, plus nodes with
     no stored record.
   - **orphans**: stored `node_id`s absent from the live graph.
   - **current**: nodes whose `doc_hash` matches — reused, not re-embedded.
4. `deleteNodes` the orphan set.
5. Batch the stale set through the `EmbeddingProvider` and `upsert` the results.
6. Write `CASEmbeddingIndex` onto `CASOutput.embedding_index`.

This reconciliation is the single correctness path. It runs identically on full and
incremental analysis. `changeReport.details` MAY be used only as a fast-path hint to
shortcut step 1 when the analyzer can prove no enriched neighbor changed; it MUST NOT
be the sole driver, because a node's embedding document includes enriched metadata
(`framework_role`, `intent`, `risk`, parent scope) that can change when a neighbor
changes without the node itself appearing in `changeReport.details`.

`EmbeddingPhase` MUST run under a wall-clock budget (`embedding.phaseBudgetMs`,
default 120000) and a provider concurrency cap. The embedding provider is a network
dependency on the analyzer hot path; thousands of sequential calls on a large repo
would add minutes to every run. On budget exhaustion the phase MUST stop, emit
`embedding_index.degraded = true` with a reason, and leave the remaining stale nodes
for the next analysis run to finish. `EmbeddingPhase` MUST be non-fatal: if the
provider or store fails, CAS MUST still emit with `degraded` set.

### Incremental Integration

Incremental analysis runs the same `EmbeddingPhase` reconciliation described above
against the incrementally-updated `CASOutput`. Because reconciliation diffs every
node's `doc_hash` against the manifest, it correctly captures nodes whose embedding
document changed through neighbor enrichment, deletes orphans from renamed or moved
nodes, and re-embeds only what genuinely changed.

The index MUST NOT be more than one analysis cycle behind the graph. When the
wall-clock budget defers work, `embedding_index.degraded` MUST remain `true` until a
subsequent run completes the reconciliation.

### Query Interface Additions (v1.10.0)

New and upgraded MCP tools:

| Tool | Description |
|------|-------------|
| `semantic_search` | Natural-language query returns graph-anchored ranked nodes |
| `search_nodes` | Gains a `mode` parameter: `lexical`, `semantic`, `hybrid` (default `hybrid`) |
| `get_embedding_status` | Reports model, coverage, staleness, and degradation |

The hybrid query path MUST:

1. Embed the query string with the same model recorded in `CASEmbeddingIndex`.
2. Retrieve vector top-K from the `VectorStore`.
3. Run the existing lexical match.
4. Fuse the two ranked lists with reciprocal rank fusion.
5. Apply a structural re-rank: `final = alpha * fused + beta * structural`, where the structural score rewards entry points, high connectivity, test coverage, and graph coherence with other hits.
6. Return `SemanticSearchResult` objects with `graph_context` populated.

`get_agent_work_packet`, `get_coding_context`, and `resolve_agent_analysis` MUST use the hybrid path for target inference when the task references no explicit symbol.

### Semantic Rules (v1.10.0)

#### 5.28 Embedding Storage

- Embedding vectors MUST NOT be stored inside `CASNode` or `CASOutput.nodes`.
- `CASOutput.embedding_index` MUST record `model`, `dimensions`, `document_version`, and `coverage`.
- `embedding_doc_hash` MUST use SHA256 truncated to 16 characters and MUST incorporate `implementation.body_hash`.
- The vector store manifest MUST record `cas_version`, `analysis_id`, and a CAS content hash. `EmbeddingPhase` and semantic search MUST validate these on load; on mismatch the index is treated as `degraded`.
- `FileVectorStore` MUST write `index.bin` and `manifest.json` atomically via temp-file rename.

#### 5.29 Index Reconciliation

- Every analysis run, full or incremental, MUST reconcile the stored embedding set against the live node-ID set: re-embed nodes whose `doc_hash` changed, and delete embeddings whose `node_id` is absent from the live graph (orphans from deletions, renames, and moves).
- `changeReport.details` MUST NOT be the sole driver of re-embedding; it is a fast-path hint only.
- A node present in CAS without a current embedding MUST be counted in `coverage.skipped` or `coverage.failed`, never silently omitted.

#### 5.30 Query Correctness

- Query embeddings MUST use the model recorded in `CASEmbeddingIndex`.
- On model or dimension mismatch, semantic search MUST fall back to lexical and set `degraded` in the response.
- Hybrid fusion MUST be deterministic for a fixed index and query.
- The exact-match floor: a node with an exact lexical match on `name` or `qualified_name` MUST appear within the top K results. When multiple nodes share an exact name, all MUST appear within top K and their relative order MUST follow `scores.final`; the floor lifts them into the result window, it does not flatten their ranking.

#### 5.31 Failure Surfacing

- Embedding failure MUST be non-fatal and MUST be visible in `embedding_index`.
- `EmbeddingPhase` budget exhaustion MUST set `embedding_index.degraded` until a later run completes reconciliation.
- `get_embedding_status` MUST report when the index is stale, degraded, or absent.
- `PgVectorStore` MUST validate `config.embedding.dimensions` against the live column dimension on boot and refuse to start on mismatch.

### Migration Guide

#### Upgrading from v1.9.0 to v1.10.0

**Required changes:**
- Update `cas_version` to "1.10.0".

**Optional enhancements:**
- Configure `.klaurorc` `embedding` block.
- Run the `node_embeddings` migration for hosted deployments.
- Adopt `semantic_search` and the `mode` parameter on `search_nodes`.

**Breaking changes:**
- None. `embedding_index` is optional. Consumers that ignore it are unaffected. Existing analyses without an index continue to serve lexical search.

## Proof Requirements

Add a semantic-retrieval benchmark, `npm run semantic-retrieval-benchmark`:

- A fixture of natural-language queries with known target node IDs across the gauntlet repos.
- Report recall@5, recall@10, and MRR for `lexical`, `semantic`, and `hybrid` modes.
- Acceptance requires `hybrid` recall@10 to exceed `lexical` recall@10 by a positive margin with no MRR regression.

Add a live copied-repo A/B trial:

- Tasks describe the target conceptually, with no class or file named.
- The with-Klauro arm uses `semantic_search` for target inference; the control arm cannot use CAS or MCP.
- The evaluator scores correctness, target-file accuracy, token usage, and wall time.
- Acceptance requires no correctness regression and a positive token or time delta on no-target tasks.

Existing gauntlets MUST NOT regress:

- `agent-gauntlet`, `analysis-gauntlet`, `agent-quality-benchmark`, and the incremental-value benchmark MUST still pass at their current thresholds.

## Acceptance Criteria

- CAS v1.10.0 emits `embedding_index` on representative NestJS, React, Python, Rust, and mixed repositories.
- `FileVectorStore` and `PgVectorStore` both pass upsert, delete, and query correctness checks.
- `semantic_search` returns graph-anchored results; hybrid recall@10 beats the lexical baseline.
- Incremental analysis re-embeds only changed nodes and leaves zero index staleness.
- Embedding failure is non-fatal and surfaced through `embedding_index` and `get_embedding_status`.
- No regression on existing gauntlets.

## Resolved Decisions

Settled during the independent review:

1. **Embedding model.** Default to `voyage-code-3`, a code-specialized model. Retrieval quality dominates; the structural re-rank cannot rescue a weak candidate set. The model and `document_version` are pinned in `embedding_index`. The API key is required config when `provider: "api"`.
2. **int8 quantization.** In scope for v1.10.0, not deferred. `FileVectorStore` stores int8-quantized vectors with a per-vector scale. Cuts memory roughly fourfold and keeps brute-force cosine fast past 50k nodes.
3. **Structural re-rank weights.** `alpha` and `beta` are fixed constants in v1.10.0, exposed in config as an escape hatch. They MUST be chosen on a held-out query split, never the gauntlet fixture used for acceptance, to keep the proof non-circular. Per-repo learned weights are deferred.
4. **Query-embedding cache.** Yes. An LRU keyed by `sha256(query + model)` removes a network round-trip per MCP call; agents re-issue near-identical queries within a session.
5. **pgvector index.** HNSW, not IVFFlat: IVFFlat needs a populated table to train and degrades under the continuous upserts of an always-fresh index. Build parameters `m = 16, ef_construction = 64`, query-time `ef_search = 100`. The table is partitioned by `analysis_id` so each tenant's HNSW index is isolated.
